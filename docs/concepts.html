1. Application core

QApplication and the event loop Step 1

Every Qt GUI begins with a QApplication. It initializes the GUI subsystem, parses Qt-specific command-line flags (-style, -platform, …), and — crucially — runs the event loop when you call exec(). The event loop is the heartbeat of any Qt GUI: it pulls events (mouse, keyboard, paint, timer) from the OS and dispatches them to widgets. Without it, your window appears and instantly closes.

// src/main.cpp — entry point
int main(int argc, char *argv[])
{
    QApplication app(argc, argv);
    QApplication::setApplicationName("InferenceVisualizer");
    QApplication::setApplicationVersion("0.1.0");

    installFileLogger();

    MainWindow window;
    window.show();

    return QApplication::exec();   // runs the event loop until quit
}

src/main.cpp:67–79

Keep main() tiny Step 1

Anything inside main is hard to test, hard to depend on, and hard to refactor. Our main.cpp only constructs QApplication, installs the log handler, shows the MainWindow, and enters the event loop. All real logic lives in classes that can be exercised independently — see the snippet for QApplication above; that is the entire body of main.

tr() for translatable strings Step 1

Every user-visible string is wrapped in tr("…"). Even with no translation files today, the habit costs nothing and means localizing later is a tooling problem instead of a refactor.

// src/app/MainWindow.cpp — every user-facing string uses tr()
setWindowTitle(tr("InferenceVisualizer"));
statusBar()->showMessage(tr("Ready."));
auto *fileMenu = menuBar()->addMenu(tr("&File"));

2. The Qt object system

The Q_OBJECT macro and the MOC Step 1

Any class that uses signals, slots, properties, or runtime type info needs Q_OBJECT in its declaration. The macro declares hidden meta-object members; the Meta-Object Compiler (MOC) reads your header at build time and generates a moc_*.cpp file with their implementations. Without Q_OBJECT, connect() calls compile but silently fail to fire — or you get "undefined reference to vtable" link errors. CMake's AUTOMOC (enabled by qt_standard_project_setup()) runs MOC for you on any header containing the macro.

// src/app/MainWindow.h — any class with signals/slots needs Q_OBJECT
class MainWindow : public QMainWindow
{
    Q_OBJECT                       // MOC processes this header because of this line

public:
    explicit MainWindow(QWidget *parent = nullptr);

private slots:
    void openImage();
    void openVideo();
    // ...
};

Parent–child ownership Step 1

When you pass a parent pointer to a QObject constructor — new QLabel(this) — the child is added to the parent's child list. When the parent is destroyed, Qt walks that list and deletes every child. This is why raw new/delete in Qt code isn't a leak: the lifetime is encoded in the parent tree, not in std::unique_ptr. Don't mix the two for the same object.

// src/ui/ImageView.cpp — m_label is auto-deleted when ImageView is destroyed
ImageView::ImageView(QWidget *parent)
    : QWidget(parent)
    , m_label(new QLabel(this))    // "this" is the parent
{
    // ... no delete needed anywhere ...
}

Signals & slots (modern syntax) Step 1

A signal is emitted when something happens (QAction::triggered fires when the user clicks the menu entry). A slot is a function that runs in response. connect() wires them together. We use the function-pointer form, which is checked at compile time:

// src/app/MainWindow.cpp — menu action wired to a slot
auto *openImageAction = fileMenu->addAction(tr("&Open Image..."));
openImageAction->setShortcut(QKeySequence::Open);
connect(openImageAction, &QAction::triggered, this, &MainWindow::openImage);

If the signal doesn't exist or the slot signature doesn't match, you get a compile error. The old string-based form SIGNAL(triggered())/SLOT(openImage()) is checked at runtime and fails silently on typos. Always prefer the function-pointer form.

src/app/MainWindow.cpp:62–74

Connecting to a lambda Step 2

connect() accepts a callable instead of a member function pointer. The third argument (the "context object") matters: it ties the lambda's lifetime to the context so the connection is automatically disconnected if the context object is destroyed before the signal fires.

// src/ui/VideoControls.cpp — tiny inline slot, context = this
connect(m_slider, &QSlider::sliderPressed, this,
        [this]() { m_userIsDragging = true; });

Always pass a context object with lambda slots; the two-argument form without context is a common source of use-after-free bugs in Qt code.

src/ui/VideoControls.cpp:40–41

Signal forwarding (the façade pattern) Step 2

A connect() can wire a signal directly to another signal. When the first fires, the second fires automatically with the same arguments. This is how VideoController hides QMediaPlayer: it re-exports the player's signals through its own API.

// src/media/VideoController.cpp — signal-to-signal connects = a stable facade
connect(m_player, &QMediaPlayer::playbackStateChanged,
        this,     &VideoController::playbackStateChanged);
connect(m_player, &QMediaPlayer::positionChanged,
        this,     &VideoController::positionChanged);
connect(m_player, &QMediaPlayer::durationChanged,
        this,     &VideoController::durationChanged);

Nothing outside VideoController.cpp ever needs to know about QMediaPlayer. Tomorrow we could swap the backend for cv::VideoCapture and connections to VideoController::positionChanged keep working.

src/media/VideoController.cpp:24–32

Q_DISABLE_COPY Step 1

A Qt-provided macro that deletes the copy constructor and copy assignment operator. QObjects have identity (signals are connected to specific instances), so copying them rarely means what you'd expect. Adding it makes accidental copies a compile error.

// src/ui/ImageView.h — bottom of the class body
class ImageView : public QWidget
{
    Q_OBJECT
    // ... members and methods ...
private:
    QLabel *m_label;
    QImage  m_original;

    Q_DISABLE_COPY(ImageView)      // no accidental copies
};

3. Widgets & layouts

QMainWindow vs plain QWidget Step 1

QMainWindow is a specialized window that provides slots for a menu bar, status bar, toolbars, dock widgets, and a single central widget. Use it for the top-level window. Use plain QWidget (or a subclass) for custom widgets that live inside other widgets — like our ImageView.

// src/app/MainWindow.h — top-level window: QMainWindow
class MainWindow : public QMainWindow { /* menus, status bar, central widget */ };

// src/ui/ImageView.h — reusable inner widget: QWidget
class ImageView  : public QWidget     { /* just a QLabel + scaling */ };

QSplitter — draggable dual-pane layout Step 2

A container widget with a draggable divider between its children. setStretchFactor controls how extra space is distributed; setChildrenCollapsible(false) prevents the divider from being dragged all the way to one side and hiding a pane (an easy way to lose your UI).

// src/app/MainWindow.cpp — the dual-pane central widget
auto *splitter = new QSplitter(Qt::Horizontal);
splitter->addWidget(m_originalView);
splitter->addWidget(m_processedView);
splitter->setStretchFactor(0, 1);
splitter->setStretchFactor(1, 1);
splitter->setChildrenCollapsible(false); // prevents zero-width panes

A horizontal or vertical numeric slider. setRange(min, max) sets bounds; setSingleStep / setPageStep control keyboard nudging; setTracking(true) makes sliderMoved fire continuously while dragging (versus only on release).

QAction, QMenu, QMenuBar Step 1

An action represents something the user can do, decoupled from where it appears. The same QAction can live in a menu, a toolbar, and a context menu simultaneously, with one shortcut and one icon. That decoupling is why Qt models commands this way even when you only use the action from one menu.

Layouts (QVBoxLayout, QHBoxLayout) Step 1

Layouts handle widget positioning and resize propagation automatically. We use a zero-margin QVBoxLayout in ImageView; a QHBoxLayout in VideoControls. Hand-rolling setGeometry() works but is fragile — always reach for a layout first.

layout->setContentsMargins(0, 0, 0, 0);
layout->addWidget(m_label);

// src/ui/VideoControls.cpp — horizontal: button | slider (stretch) | label
auto *layout = new QHBoxLayout(this);
layout->setContentsMargins(6, 4, 6, 4);
layout->addWidget(m_playPauseBtn);
layout->addWidget(m_slider, /*stretch=*/1);
layout->addWidget(m_timeLabel);

4. Events

resizeEvent overrides Step 1

Qt delivers events to widgets through virtual methods on QWidget: paintEvent, mousePressEvent, resizeEvent, … Override the one you care about. Always call the base-class implementation unless you specifically intend to suppress the default behaviour.

// src/ui/ImageView.h — declaration
protected:
    void resizeEvent(QResizeEvent *event) override;

// src/ui/ImageView.cpp — rescale the displayed pixmap whenever we change size
void ImageView::resizeEvent(QResizeEvent *event)
{
    QWidget::resizeEvent(event);    // always chain to the base
    if (!m_original.isNull()) {
        updateScaledPixmap();
    }
}

5. Images & pixels

QImage vs QPixmap Step 1

Two pixel containers, used at different stages of the pipeline:

QImageQPixmap
Lives onCPU memoryDisplay server / GPU (platform-dependent)
Thread-safe?Yes — safe to create/use on any threadNo — GUI thread only
Best forLoading, processing, inference, storageDrawing to a widget

Rule of thumb: store QImage, convert to QPixmap at the last moment when assigning to a QLabel.

// src/ui/ImageView.cpp — we keep m_original as QImage; QPixmap only at the moment of drawing
const QPixmap pixmap = QPixmap::fromImage(m_original).scaled(
    target,
    Qt::KeepAspectRatio,
    Qt::SmoothTransformation);
m_label->setPixmap(pixmap);

This rule will matter a great deal in Step 3, when inference runs on a worker thread — the result must come back as a QImage.

src/ui/ImageView.cpp:58–63

QImageReader over QImage(path) Step 1

Both can load images, but QImageReader exposes errorString(), lets you query the file's format without loading it, and provides setAutoTransform(true) to honour EXIF orientation. The constructor form gives you a generic null image on failure with no clue why.

// src/app/MainWindow.cpp — robust image loading with diagnosable errors
QImageReader reader(path);
reader.setAutoTransform(true);             // honour EXIF orientation
const QImage image = reader.read();

if (image.isNull()) {
    QMessageBox::warning(this, tr("Could not open image"),
        tr("Failed to load \"%1\":\n%2").arg(path, reader.errorString()));
    return;
}

src/app/MainWindow.cpp:120–129

Rescale from the original, every time Step 1

Each scale-down loses information. If you scale on every resize starting from the previously-scaled pixmap, quality decays visibly. ImageView::updateScaledPixmap() always starts from the stored QImage, never from the current QPixmap.

// src/ui/ImageView.cpp — resize-safe rescale
void ImageView::updateScaledPixmap()
{
    // Always rescale from the original. Rescaling a scaled pixmap repeatedly
    // produces visible quality loss as the user resizes the window.
    const QSize target = m_label->size();
    if (target.isEmpty()) return;

    const QPixmap pixmap = QPixmap::fromImage(m_original).scaled(
        target,
        Qt::KeepAspectRatio,
        Qt::SmoothTransformation);
    m_label->setPixmap(pixmap);
}

6. Files & user interaction

QFileDialog::getOpenFileName Step 1

A static convenience function that pops up the OS file picker and blocks until the user chooses a file or cancels. Returns an empty QString on cancel — not an error, just nothing to do. The filter string is built dynamically from QImageReader::supportedImageFormats() so any plugin Qt picks up at runtime (WebP, AVIF, …) is automatically included.

// src/app/MainWindow.cpp — image file picker with plugin-aware filter
QStringList patterns;
for (const QByteArray &fmt : QImageReader::supportedImageFormats()) {
    patterns << QStringLiteral("*.%1").arg(QString::fromLatin1(fmt));
}
const QString filter = tr("Images (%1);;All files (*)").arg(patterns.join(' '));

const QString path = QFileDialog::getOpenFileName(
    this, tr("Open Image"), QString(), filter);
if (path.isEmpty()) return;                // user cancelled

7. Multimedia pipeline

QMediaPlayer — the playback engine Step 2

The high-level media-playback object in Qt Multimedia. You hand it a URL via setSource(), call play() / pause() / stop() / setPosition(), and it delegates to a platform backend (FFmpeg on your install) to decode audio and video. It exposes signals for playbackStateChanged, positionChanged, durationChanged, mediaStatusChanged, and errorOccurred. It does not render anything by itself — you give it a sink to send frames to.

// src/media/VideoController.cpp — create the player, attach a sink, open a file
VideoController::VideoController(QObject *parent)
    : QObject(parent)
    , m_player(new QMediaPlayer(this))
    , m_sink(new QVideoSink(this))
{
    m_player->setVideoSink(m_sink);
    // ... connect signals ...
}

bool VideoController::openFile(const QString &path)
{
    m_player->stop();
    m_player->setSource(QUrl::fromLocalFile(path));
    return true;
}

src/media/VideoController.cpp:10–15,43–54

QVideoSink + QVideoFrame — the frame tap Step 2

QVideoSink is a frame consumer object. Attach it to a player with setVideoSink(sink) and decoded frames arrive as QVideoFrame objects via the videoFrameChanged signal — on the GUI thread. QVideoFrame holds the raw pixel data in whatever format the decoder produced (typically YUV from FFmpeg); frame.toImage() performs the colour conversion to QImage for display or inference.

// src/media/VideoController.cpp — connect the sink and translate frames to QImage
connect(m_sink, &QVideoSink::videoFrameChanged,
        this,   &VideoController::handleVideoFrame);

// ...

void VideoController::handleVideoFrame(const QVideoFrame &frame)
{
    if (!frame.isValid()) return;
    const QImage image = frame.toImage();   // YUV -> RGB happens here
    if (image.isNull()) return;
    emit frameReady(image);
}

The alternative — QVideoWidget — renders directly to the screen but gives you no way to intercept frames, which would block Step 3 entirely.

src/media/VideoController.cpp:18–19,79–107

MediaStatus vs PlaybackState Step 2

Two different state machines on QMediaPlayer, easy to confuse:

  • PlaybackState: StoppedState / PlayingState / PausedState. What the user sees on the play/pause button.
  • MediaStatus: NoMedia → LoadingMedia → LoadedMedia → BufferingMedia → BufferedMedia → EndOfMedia, plus InvalidMedia on decode failure. The diagnostic state machine.
// src/media/VideoController.cpp — status changes are the most informative diagnostic
void VideoController::handleMediaStatus(QMediaPlayer::MediaStatus status)
{
    const char *name = "?";
    switch (status) {
        case QMediaPlayer::NoMedia:        name = "NoMedia";        break;
        case QMediaPlayer::LoadingMedia:   name = "LoadingMedia";   break;
        case QMediaPlayer::LoadedMedia:    name = "LoadedMedia";    break;
        case QMediaPlayer::StalledMedia:   name = "StalledMedia";   break;
        case QMediaPlayer::BufferingMedia: name = "BufferingMedia"; break;
        case QMediaPlayer::BufferedMedia:  name = "BufferedMedia";  break;
        case QMediaPlayer::EndOfMedia:     name = "EndOfMedia";     break;
        case QMediaPlayer::InvalidMedia:   name = "InvalidMedia";   break;
    }
    qDebug() << "[VideoController] mediaStatus =" << name;

    if (status == QMediaPlayer::InvalidMedia) {
        emit errorOccurred(tr("Codec/container unsupported, or file is corrupt."));
    }
}

When something goes wrong, log mediaStatus transitions first; the PlaybackState will eventually catch up but tells you nothing about cause.

8. UI patterns drawn from the codebase

Slider drag/update interlock Step 2

When the controller calls VideoControls::setPosition() 30×/second to advance the slider, that's fine — unless the user is mid-drag. Naïve code yanks the thumb out from under their finger. The fix is a small state machine.

// src/ui/VideoControls.cpp — the press/release flag pattern
connect(m_slider, &QSlider::sliderPressed, this,
        [this]() { m_userIsDragging = true; });
connect(m_slider, &QSlider::sliderReleased,
        this,     &VideoControls::onSliderReleased);

// ...

void VideoControls::setPosition(qint64 milliseconds)
{
    m_position = milliseconds;
    if (!m_userIsDragging) {                // don't fight the user's finger
        m_slider->setValue(static_cast<int>(milliseconds));
    }
    updateTimeLabel();
}

void VideoControls::onSliderReleased()
{
    m_userIsDragging = false;
    emit seekRequested(static_cast<qint64>(m_slider->value())); // one seek on release
}

This is a generally applicable pattern any time external state and user input fight for the same widget.

9. Deployment & runtime on Windows

Windows DLL search order Step 2

When the OS loads an executable, it resolves DLL references in roughly this order:

  1. The application directory.
  2. System32, SysWOW64.
  3. Directories listed in PATH.

So a Qt6Core.dll sitting next to your .exe always beats one on PATH. This matters when something has deployed Qt DLLs into your build/bin/ — you may be loading a different copy than you think.

Qt's plugin discovery (separate from the OS) Step 2

Qt's modules (Multimedia, image formats, platform integration, SQL drivers, etc.) are loaded at runtime from plugins/<category>/*.dll. Qt searches a list of paths returned by QCoreApplication::libraryPaths():

  1. The application directory + a plugins subfolder, if one exists.
  2. The path baked into Qt6Core.dll at the time Qt was built (usually the Qt install's plugins/ dir).
  3. Any directory pointed to by the QT_PLUGIN_PATH environment variable.

If a Qt6Core.dll from one Qt install ends up next to your .exe (typically copied there by a half-run of windeployqt), its baked-in path may not match where your plugins actually live, and things like QMediaPlayer silently become no-ops with Available backends QList(). Setting QT_PLUGIN_PATH in launch.json is the development fix; windeployqt doing a clean full deployment is the distribution fix.

windeployqt Step 2

Qt's bundled tool that walks an .exe, figures out which Qt DLLs and plugins it needs, and copies them next to the executable along with a generated qt.conf that fixes up the plugin search path. Run it once when you want a self-contained distribution; never run it half-way or you get the plugin discovery landmine.

# PowerShell — turn a built .exe into a self-contained deployment
C:\Qt\6.11.1\mingw_64\bin\windeployqt.exe `

10. Diagnostics & logging

Where qDebug() goes on Windows Step 2

On Windows, a Qt GUI app (linked with the WIN32 subsystem flag) detaches from the console. qDebug() output goes to OutputDebugString instead of stdout. VS Code's cppdbg debug console does not show OutputDebugString output — only Sysinternals' DbgView does. Qt Creator's "Application Output" pane captures it for you — so in Qt Creator it just works, anywhere else it appears to vanish.

qInstallMessageHandler — redirecting Qt logs Step 2

The robust workaround for the routing problem above: install a custom message handler that writes to a log file. The handler is called for every qDebug/qInfo/qWarning/qCritical/qFatal; we format, timestamp, and append. Truncating on each launch keeps the file scoped to one run.

// src/main.cpp — the message handler itself
void fileMessageHandler(QtMsgType type, const QMessageLogContext &ctx, const QString &msg)
{
    QMutexLocker lock(&g_logMutex);
    if (!g_logFile.isOpen()) return;

    const char *level = "DBG ";
    switch (type) {
        case QtDebugMsg:    level = "DBG "; break;
        case QtInfoMsg:     level = "INFO"; break;
        case QtWarningMsg:  level = "WARN"; break;
        case QtCriticalMsg: level = "CRIT"; break;
        case QtFatalMsg:    level = "FATL"; break;
    }
    g_logStream << QDateTime::currentDateTime().toString("HH:mm:ss.zzz")
                << ' ' << level << ' ' << msg << '\n';
    g_logStream.flush();
}

// installFileLogger() truncates the file and registers the handler
void installFileLogger()
{
    const QString path = QCoreApplication::applicationDirPath()
                       + QStringLiteral("/inference-visualizer.log");
    g_logFile.setFileName(path);
    if (g_logFile.open(QIODevice::WriteOnly | QIODevice::Truncate | QIODevice::Text)) {
        g_logStream.setDevice(&g_logFile);
        qInstallMessageHandler(fileMessageHandler);
    }
}

Combined with the file message handler, this gives you a record of which plugin loaded, which codec was chosen, and why playback failed if it did.

11. Modern C++ patterns

#pragma once Step 1

Replaces traditional #ifndef/#define/#endif header guards. Supported by every modern compiler (GCC, Clang, MSVC), one line instead of three, no risk of macro-name collisions across files.

// src/ui/ImageView.h — one-line header guard
#pragma once

#include <QImage>
#include <QWidget>

Pure virtual functions & abstract interfaces Step 3

A pure virtual function is declared with = 0. A class with at least one pure virtual is abstract: you can't instantiate it directly; only subclasses that override every pure virtual become concrete. This is C++'s way of expressing "interface" — same role as interface in Java or protocol in Swift.

// src/inference/IInferenceBackend.h — abstract base class
class IInferenceBackend
{
public:
    virtual ~IInferenceBackend() = default;       // always virtual destructor on base classes

    virtual bool    loadModel(const QString &path) = 0;
    virtual bool    isReady() const = 0;
    virtual QString errorString() const = 0;
    virtual QImage  infer(const QImage &input) = 0;
    virtual void    setOverlayOpacity(double opacity) = 0;
};

Two non-obvious rules worth remembering:

  • Always declare the destructor virtual on a class meant to be used through a base pointer. Without it, delete basePtr only calls the base destructor, leaking the derived part. virtual ~Foo() = default; on the abstract class is the idiomatic fix.
  • The cost is one vtable indirection per virtual call. Negligible compared to inference (~50 ms); important to consider in tight inner loops. We're well outside any tight loop.

PIMPL: hiding library headers behind a pointer Step 3

The "pointer to implementation" idiom: declare an opaque struct Impl in the header, define it in the .cpp. Useful when a class's implementation pulls in a big or messy header you don't want every consumer to drag in. We use it to keep onnxruntime_cxx_api.h out of OnnxRunner.h, so only OnnxRunner.cpp sees that header.

// src/inference/OnnxRunner.h — forward-decl what we need, opaque Impl

    struct Env;
    struct Session;
    struct SessionOptions;
}

class OnnxRunner
{
public:
    OnnxRunner();
    ~OnnxRunner();
    // ...
private:
    struct Impl;                            // declared here, defined in .cpp
    std::unique_ptr<Impl> m_impl;
};

// src/inference/OnnxRunner.cpp — the real ORT types live here only
#include <onnxruntime_cxx_api.h>

struct OnnxRunner::Impl {
    Ort::Env                       env{ORT_LOGGING_LEVEL_WARNING, "InferenceVisualizer"};
    Ort::SessionOptions            options;
    std::unique_ptr<Ort::Session>  session;
    Ort::AllocatorWithDefaultOptions allocator;
    std::vector<Ort::Value>        lastOutputs;
};

Costs and benefits:

  • Faster compiles. Files including OnnxRunner.h don't transitively include 50+ ONNX Runtime headers.
  • Cleaner ABI. Adding members to Impl doesn't change OnnxRunner's layout; downstream code doesn't recompile.
  • One extra indirection on every member access. Negligible for our setup-cost class; avoid PIMPL in hot inner loops.
  • Destructor must be defined in the .cpp, not = default in the header — otherwise the compiler tries to instantiate ~Impl where Impl is incomplete and errors out. (We do ~OnnxRunner() = default; in the .cpp, which is fine.)

Preprocessing: QImage → NCHW float tensor Step 3

ONNX models from PyTorch nearly always expect NCHW layout: a 4-D tensor of [batch, channels, height, width], with channels stored as separate planes (first all R values, then all G, then all B). NHWC is the alternative (channels interleaved per pixel) but very rare for PyTorch-exported models.

The transform from QImage to NCHW is: resize to model input dimensions, convert to RGB888, scale to [0, 1] floats, normalize with per-channel mean/std (whatever the model was trained with — ImageNet defaults shown below), and pack into three contiguous planes.

// src/inference/OnnxSegmentationBackend.cpp — build the NCHW float buffer
QImage resized = input.scaled(W, H, Qt::IgnoreAspectRatio,
                              Qt::SmoothTransformation);
if (resized.format() != QImage::Format_RGB888) {
    resized = resized.convertToFormat(QImage::Format_RGB888);
}

m_inputBuffer.assign(static_cast<size_t>(C * H * W), 0.0f);

const float invStdR = 1.0f / m_cfg.std_[0];
const float invStdG = 1.0f / m_cfg.std_[1];
const float invStdB = 1.0f / m_cfg.std_[2];

for (int y = 0; y < H; ++y) {
    const uchar *line = resized.constScanLine(y);
    for (int x = 0; x < W; ++x) {
        const float r = line[x * 3 + 0] / 255.0f;
        const float g = line[x * 3 + 1] / 255.0f;
        const float b = line[x * 3 + 2] / 255.0f;
        m_inputBuffer[0 * H * W + y * W + x] = (r - m_cfg.mean[0]) * invStdR;   // R plane
        m_inputBuffer[1 * H * W + y * W + x] = (g - m_cfg.mean[1]) * invStdG;   // G plane
        m_inputBuffer[2 * H * W + y * W + x] = (b - m_cfg.mean[2]) * invStdB;   // B plane
    }
}

Postprocessing: YOLOv8 instance-segmentation decode Step 3

The Step 3 model is a YOLOv8 instance-segmentation network, not a pure semantic-segmentation one. Its two outputs have a totally different shape: a per-anchor tensor of bbox+classes+mask-coefficients, and a tensor of mask prototypes. The post-processing pipeline:

  1. Decode each of the 8400 anchors into a candidate detection: box (xywh), best class score, 32 mask coefficients. Drop anything below the confidence threshold (default 0.25).
  2. Non-max suppression (NMS) within each class: sort by score desc, suppress later detections whose IoU with an earlier one exceeds 0.7.
  3. Per-surviving-detection mask = sigmoid( mask_coeffs · mask_prototypes ), giving a 160×160 mask per instance. Binarise at 0.5; paint inside its bbox with the class color.
// src/inference/OnnxSegmentationBackend.cpp — decode + NMS over YOLO output0
for (int i = 0; i < anchors; ++i) {
    int   bestC = 0;
    float bestS = val(clsOff, i);
    for (int c = 1; c < m_cfg.numClasses; ++c) {
        const float s = val(clsOff + c, i);
        if (s > bestS) { bestS = s; bestC = c; }
    }
    if (bestS < m_cfg.confidenceThreshold) continue;

    // xywh -> xyxy (in model input space, e.g. 640x640)
    Detection d;
    d.x1 = val(0, i) - val(2, i) * 0.5f;
    d.y1 = val(1, i) - val(3, i) * 0.5f;
    d.x2 = val(0, i) + val(2, i) * 0.5f;
    d.y2 = val(1, i) + val(3, i) * 0.5f;
    d.score = bestS;
    d.classId = bestC;
    d.maskCoeffs.resize(m_cfg.numMaskCoeffs);
    for (int k = 0; k < m_cfg.numMaskCoeffs; ++k) {
        d.maskCoeffs[k] = val(maskOff + k, i);
    }
    candidates.push_back(std::move(d));
}
// src/inference/OnnxSegmentationBackend.cpp — per-detection mask = sigmoid(coeffs @ prototypes)
for (int y = 0; y < ph; ++y) {
    for (int x = 0; x < pw; ++x) {
        float sum = 0.f;
        for (int k = 0; k < nm; ++k) {
            sum += d.maskCoeffs[k] * proto(k, y, x);
        }
        instMask[y * pw + x] = 1.f / (1.f + std::exp(-sum));   // sigmoid
    }
}

Controller-as-orchestrator (FIFO + backpressure) Step 3

InferenceController owns the backend, receives QImage frames from outside (an image open, a video frame), runs them through the backend in arrival order, emits the result. Three design properties:

  1. Always emits a processedFrameReady signal, even when inference is disabled — the emitted image is just the input unchanged. This keeps Step 2's dual-pane mirror behavior working with zero special-case wiring in MainWindow.
  2. Process every frame, in order, never drop. Frames are appended to a FIFO. Each frame is processed exactly once. This is what the user actually wants for offline-style inference: every frame matters.
  3. Backpressure to the source. When the FIFO grows past a high watermark, the controller emits wantsSourcePaused(true); MainWindow forwards that to the video player, which pauses. When the queue drains to a low watermark, the controller emits wantsSourcePaused(false) and the player resumes. The hysteresis (high vs low) prevents pause/resume thrashing every single frame.
// src/app/InferenceController.cpp — FIFO enqueue + backpressure on high watermark
void InferenceController::processFrame(const QImage &input)
{
    if (!m_enabled || !isReady() || input.isNull()) {
        emit processedFrameReady(input);   // passthrough preserves Step 2 mirror
        return;
    }

    m_frameQueue.enqueue(input);            // FIFO: never drop, never reorder

    if (!m_backpressured && m_frameQueue.size() >= m_highWatermark) {
        m_backpressured = true;
        emit wantsSourcePaused(true);       // MainWindow pauses the video
    }

    if (!m_busy) {
        m_busy = true;
        QMetaObject::invokeMethod(this,
            &InferenceController::runNextQueuedFrame,
            Qt::QueuedConnection);          // next event-loop tick, not now
    }
}
// src/app/InferenceController.cpp — pull one, infer, release backpressure, loop
void InferenceController::runNextQueuedFrame()
{
    if (m_frameQueue.isEmpty() || !isReady() || !m_enabled) {
        m_busy = false;
        if (m_backpressured) {
            m_backpressured = false;
            emit wantsSourcePaused(false);
        }
        return;
    }

    QImage frame = m_frameQueue.dequeue();
    QImage result = m_backend->infer(frame);   // blocks GUI; step 4 fixes
    emit processedFrameReady(result.isNull() ? frame : result);

    if (m_backpressured && m_frameQueue.size() <= m_lowWatermark) {
        m_backpressured = false;
        emit wantsSourcePaused(false);          // MainWindow resumes the video
    }

    if (!m_frameQueue.isEmpty()) {
        QMetaObject::invokeMethod(this,
            &InferenceController::runNextQueuedFrame,
            Qt::QueuedConnection);              // re-queue, NOT a tight while loop
    } else {
        m_busy = false;
    }
}

The user's experience: when CPU inference is much slower than the video frame period (e.g. 3 sec per frame on a 30 fps video), the video plays in short bursts — decode a couple of frames, the queue hits the high watermark, video pauses, inference grinds through the queue, video resumes when caught up. Every frame in the video appears on the processed pane in its native order. Memory stays bounded at the high watermark (typically 2–4 frames buffered). The MainWindow side tracks whether it initiated the pause (vs. the user clicking pause) so user pauses are never auto-resumed.

This is the standard producer-consumer backpressure pattern. The simpler "drop intermediate frames" variant of this is also useful when you want the most-recent frame regardless of order (real-time monitoring); for batch-style inference where you can't lose anything, FIFO + backpressure is the right shape. Step 4 (worker-thread inference) lifts inference off the GUI thread; the FIFO + backpressure pattern is still the right shape for the cross-thread channel.

13. Image overlays with QPainter

Compositing a mask onto an image Step 3

The mask we built in postprocessing is an ARGB QImage at the original image's display size: every pixel is either fully opaque colored (for visible classes) or fully transparent (for hidden or background classes). To draw it on top of the input image, we use QPainter with a single global opacity for the mask layer.

// src/inference/OnnxSegmentationBackend.cpp — QPainter composite
QImage OnnxSegmentationBackend::compositeOverlay(
    const QImage &original,
    const QImage &mask) const
{
    QImage result = original.convertToFormat(QImage::Format_ARGB32);

    QPainter painter(&result);
    painter.setRenderHint(QPainter::SmoothPixmapTransform, false);
    painter.setOpacity(m_opacity);            // 0.0 .. 1.0; user-controllable
    painter.drawImage(0, 0, mask);
    painter.end();

    return result;
}

Key things going on:

  • QPainter::setOpacity applies a uniform alpha to every subsequent drawing operation. Simpler than per-pixel qRgba(...,alpha) and lets the UI vary opacity at runtime without re-running inference.
  • convertToFormat(Format_ARGB32) ensures the destination has an alpha channel. Painting on an RGB888 image silently drops alpha and the overlay won't blend correctly.
  • Nearest-neighbour scaling when the mask was scaled up to display size (see postprocessing). Smooth scaling would bleed class colors into each other at boundaries — we want hard edges.
  • painter.end() isn't strictly required (destructor calls it) but is cheap insurance against subtle bugs if you return a QImage by value while the painter is still active.

14. Common pitfalls

Forgetting Q_OBJECT. Step 1 Without it, connect() compiles but does nothing — or you get undefined reference to vtable at link time. Any class with signals, slots, or properties needs it.
Using QPixmap off the GUI thread. Step 1 QPixmap is platform-tied to the display server. Loading or constructing one on a worker thread is an instant crash on Windows and undefined behavior elsewhere. Always do the QImage → QPixmap conversion on the GUI thread.
Rescaling an already-scaled pixmap. Step 1 Each scale-down loses information. If you scale on every resize starting from the previously-scaled pixmap, quality decays visibly. Always rescale from the original QImage (which is what ImageView::updateScaledPixmap() does — see §5).
Forgetting Qt::KeepAspectRatio. Step 1 The default is Qt::IgnoreAspectRatio, which stretches the image to fill the target. Easy mistake; obvious bug.
Double-parenting. Step 1 Passing a widget to a layout (layout->addWidget(child)) reparents it to the layout's owning widget. If you also passed a parent to its constructor, the new parent overrides — usually harmless, but worth knowing when debugging "why is this widget appearing nowhere?".
Mixing std::unique_ptr with Qt parent ownership. Step 1 If a QObject has a parent and sits inside a unique_ptr, both will try to delete it. Pick one ownership model per object.
Qt plugin not loaded — silent no-op. Step 2 When QMediaPlayer::play() does nothing and there's no error, the cause is almost always the multimedia plugin failing to load. Symptoms in the log: Available backends QList(), Failed to initialize QMediaPlayer "Not available". The fix on a dev box is QT_PLUGIN_PATH; on a deployed app, windeployqt.
qDebug() output invisible under VS Code. Step 2 Qt GUI apps on Windows route stdout to OutputDebugString, which cppdbg's console doesn't show. Always install a file-based message handler when you can't use Qt Creator — otherwise every diagnostic qDebug() you write vanishes into the void.
Mixing Qt installs by accident. Step 2 If something (Qt Creator's deploy step, a stray windeployqt run) copies Qt6Core.dll next to your .exe, Windows' DLL loader will pick that over anything on PATH because the application directory comes first in the search order. If the deployed copy is from a different Qt version than the rest of your environment, you get ABI-level confusion that's invisible until something fails strangely.
Slider fighting the user's finger. Step 2 Calling QSlider::setValue() from a position-update signal while the user is dragging makes the thumb jump. Always interlock with a "user is dragging" flag (pressed/released) and emit a single seek on release. See drag/update interlock.
Lambda connect() without a context object. Step 2 connect(sig, []() { /* uses captured this */ }); compiles and runs, but the connection lives forever — even after this is destroyed. Always pass this as the third argument so Qt automatically disconnects when the context object dies.
Forgot to copy onnxruntime.dll next to the .exe. Step 3 Same STATUS_DLL_NOT_FOUND (0xc0000135) story as Qt's DLLs in Step 2. CMake has a post-build copy_if_different step that puts the DLL next to the executable; if that step is removed or fails (e.g. ORT installed at a non-default path), the .exe won't start. The .vscode/launch.json also prepends the ORT lib dir to PATH as a belt-and-braces.
NCHW vs NHWC layout mismatch. Step 3 If your model expects NHWC (channels last, interleaved) but you feed it NCHW (channel planes), ORT doesn't complain — the tensor dimensions match. You just get garbage output: a uniform-class mask, or noise. Same in reverse. OnnxSegmentationBackend::buildMaskImage tries to detect output layout heuristically (channel-axis matches numClasses); on input the layout is hard-coded NCHW because that's what PyTorch exports produce.
Preprocessing mismatch (normalization). Step 3 Models are sensitive to the mean/std they were trained with. ImageNet normalization is the default in OnnxSegmentationBackend::Config; if your model used [0,1] raw or a custom mean, you'll see an overlay that's biased toward one class regardless of input. Symptom: every pixel becomes "critical" or every pixel becomes "not-critical". Fix: adjust Config::mean / Config::std_ to match training.
ORT input/output names hard-coded incorrectly. Step 3 If you hard-code "input" / "output" but your model uses "input_1" / "output_1" (Keras default) or something else, Session::Run throws with a cryptic "Invalid input name". OnnxRunner sidesteps this by reading the names from the graph after loading; only the backend's Config defaults are used before the first model is loaded.
Mixing Qt parent-child with std::unique_ptr. Step 3 InferenceController holds the backend in a unique_ptr — OK because the backend isn't a QObject. If you put a QObject in a unique_ptr and set a parent on it, both ownership systems try to delete the object. Pick one per object. Rule of thumb: QObjects → parent-child, raw pointers; everything else → smart pointers.
Calling inference on the GUI thread. Step 3 (known limitation) Step 3 runs inference on the GUI thread for simplicity. For 30 FPS video, every inference (~100–500 ms) freezes the UI for that duration. The frame-drop pattern in InferenceController keeps the backlog bounded so the app doesn't appear hung, but the processed pane still updates only at the inference rate (a few Hz). Step 4 (formerly Step 6) moves the backend behind a QThread with Qt::QueuedConnection, so the GUI stays responsive and the worker handles drops.
Unbounded signal-driven backlog. Step 3 Connecting a high-frequency producer (QVideoSink::videoFrameChanged at 30 FPS) directly to a slow consumer slot is a recipe for OOM and runaway latency. Qt's signal queue grows without bound by default. Pick one of: (a) FIFO + backpressure to the producer (what InferenceController does — preserves every frame, pauses the source when behind); (b) drop intermediate items via a one-slot replace-buffer (good when you only care about the most recent frame); (c) a periodic QTimer pull instead of a push (when sample timing matters more than every-frame).
Tight while loop instead of Qt::QueuedConnection self-reinvocation. Step 3 When runPendingInference finishes one frame and finds another pending, it'd be tempting to loop: while (m_pendingFrame.isValid()) infer(...). Don't — that's exactly the bug we just fixed. A tight loop never yields to the event loop, so paint events never run and the app freezes. The correct pattern is to re-queue yourself via QMetaObject::invokeMethod(..., Qt::QueuedConnection), which guarantees the event loop runs at least once between iterations.
