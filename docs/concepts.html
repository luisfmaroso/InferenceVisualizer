1. Application core

QApplication and the event loop Step 1

Every Qt GUI begins with a QApplication. It initializes the GUI subsystem, parses Qt-specific command-line flags (-style, -platform, …), and — crucially — runs the event loop when you call exec(). The event loop is the heartbeat of any Qt GUI: it pulls events (mouse, keyboard, paint, timer) from the OS and dispatches them to widgets. Without it, your window appears and instantly closes.
src/main.cpp:67–77

Keep main() tiny Step 1

Anything inside main is hard to test, hard to depend on, and hard to refactor. Our main.cpp only constructs QApplication, installs the log handler, shows the MainWindow, and enters the event loop. All real logic lives in classes that can be exercised independently.

tr() for translatable strings Step 1

Every user-visible string is wrapped in tr("…"). Even with no translation files today, the habit costs nothing and means localizing later is a tooling problem instead of a refactor.

2. The Qt object system

The Q_OBJECT macro and the MOC Step 1

Any class that uses signals, slots, properties, or runtime type info needs Q_OBJECT in its declaration. The macro declares hidden meta-object members; the Meta-Object Compiler (MOC) reads your header at build time and generates a moc_*.cpp file with their implementations. Without Q_OBJECT, connect() calls compile but silently fail to fire — or you get "undefined reference to vtable" link errors. CMake's AUTOMOC (enabled by qt_standard_project_setup()) runs MOC for you on any header containing the macro.
src/app/MainWindow.h:10 · src/ui/ImageView.h:16

Parent–child ownership Step 1

When you pass a parent pointer to a QObject constructor — new QLabel(this) — the child is added to the parent's child list. When the parent is destroyed, Qt walks that list and deletes every child. This is why raw new/delete in Qt code isn't a leak: the lifetime is encoded in the parent tree, not in std::unique_ptr. Don't mix the two for the same object.
src/ui/ImageView.cpp:12 · src/app/MainWindow.cpp:24

Signals & slots (modern syntax) Step 1

A signal is emitted when something happens (QAction::triggered fires when the user clicks the menu entry). A slot is a function that runs in response. connect() wires them together. We use the function-pointer form:

connect(openAction, &QAction::triggered, this, &MainWindow::openImage);

This is checked at compile time — if the signal doesn't exist or the slot signature doesn't match, you get an error. The old string-based form SIGNAL(triggered())/SLOT(openImage()) is checked at runtime and fails silently on typos. Always prefer the function-pointer form.
src/app/MainWindow.cpp:64,74

Connecting to a lambda Step 2

connect() accepts a callable instead of a member function pointer:

connect(m_slider, &QSlider::sliderPressed, this,
        [this]() { m_userIsDragging = true; });

The third argument (the "context object") matters: it ties the lambda's lifetime to this so the connection is automatically disconnected if this is destroyed before the signal fires. Always pass a context object with lambda slots; the two-argument form without context is a common source of use-after-free bugs in Qt code.
src/ui/VideoControls.cpp:40–41

Signal forwarding (the façade pattern) Step 2

A connect() can wire a signal directly to another signal. When the first fires, the second fires automatically with the same arguments. This is how VideoController hides QMediaPlayer: it re-exports the player's signals through its own API.

connect(m_player, &QMediaPlayer::positionChanged,
        this,     &VideoController::positionChanged);

Nothing outside VideoController.cpp ever needs to know about QMediaPlayer. Tomorrow we could swap the backend for cv::VideoCapture and connections to VideoController::positionChanged keep working.
src/media/VideoController.cpp:20–32

Q_DISABLE_COPY Step 1

A Qt-provided macro that deletes the copy constructor and copy assignment operator. QObjects have identity (signals are connected to specific instances), so copying them rarely means what you'd expect. Adding Q_DISABLE_COPY(ImageView) to a widget makes accidental copies a compile error.
src/ui/ImageView.h:33

3. Widgets & layouts

QMainWindow vs plain QWidget Step 1

QMainWindow is a specialized window that provides slots for a menu bar, status bar, toolbars, dock widgets, and a single central widget. Use it for the top-level window. Use plain QWidget (or a subclass) for custom widgets that live inside other widgets — like our ImageView.
src/app/MainWindow.h:8 · src/ui/ImageView.h:8

QSplitter — draggable dual-pane layout Step 2

A container widget with a draggable divider between its children. setStretchFactor controls how extra space is distributed; setChildrenCollapsible(false) prevents the divider from being dragged all the way to one side and hiding a pane (an easy way to lose your UI).
src/app/MainWindow.cpp:38–43

QSlider Step 2

A horizontal or vertical numeric slider. setRange(min, max) sets bounds; setSingleStep / setPageStep control keyboard nudging; setTracking(true) makes sliderMoved fire continuously while dragging (versus only on release). The drag/update interlock pattern (see §8 drag interlock) is essential when an external stream is also pushing values into the slider.
src/ui/VideoControls.cpp:21–30

QAction, QMenu, QMenuBar Step 1

An action represents something the user can do, decoupled from where it appears. The same QAction can live in a menu, a toolbar, and a context menu simultaneously, with one shortcut and one icon. That decoupling is why Qt models commands this way even when you only use the action from one menu.
src/app/MainWindow.cpp:62–76

Layouts (QVBoxLayout, QHBoxLayout) Step 1

Layouts handle widget positioning and resize propagation automatically. We use a zero-margin QVBoxLayout in ImageView to make the internal QLabel fill the widget; a QHBoxLayout in VideoControls arranges play button + slider + label horizontally. Hand-rolling setGeometry() works but is fragile — always reach for a layout first.
src/ui/ImageView.cpp:19–22 · src/ui/VideoControls.cpp:31–35

4. Events

resizeEvent overrides Step 1

Qt delivers events to widgets through virtual methods on QWidget: paintEvent, mousePressEvent, resizeEvent, … Override the one you care about. Always call the base-class implementation (QWidget::resizeEvent(event)) unless you specifically intend to suppress the default behaviour.
src/ui/ImageView.cpp:39–45

5. Images & pixels

QImage vs QPixmap Step 1

Two pixel containers, used at different stages of the pipeline:

QImageQPixmap
Lives onCPU memoryDisplay server / GPU (platform-dependent)
Thread-safe?Yes — safe to create/use on any threadNo — GUI thread only
Best forLoading, processing, inference, storageDrawing to a widget

Rule of thumb: store QImage, convert to QPixmap at the last moment when assigning to a QLabel. This rule will matter a great deal in Step 3, when inference runs on a worker thread — the result must come back as a QImage.
src/ui/ImageView.cpp:55–65

QImageReader over QImage(path) Step 1

Both can load images, but QImageReader exposes errorString(), lets you query the file's format without loading it, and provides setAutoTransform(true) to honour EXIF orientation (so phone photos don't appear sideways). The constructor form gives you a generic null image on failure with no clue why.
src/app/MainWindow.cpp:120–130

Rescale from the original, every time Step 1

Each scale-down loses information. If you scale on every resize starting from the previously-scaled pixmap, quality decays visibly. ImageView::updateScaledPixmap() always starts from the stored QImage, never from the current QPixmap.
src/ui/ImageView.cpp:55–65

6. Files & user interaction

QFileDialog::getOpenFileName Step 1

A static convenience function that pops up the OS file picker and blocks until the user chooses a file or cancels. Returns an empty QString on cancel — not an error, just nothing to do. The filter string is built dynamically from QImageReader::supportedImageFormats() so any plugin Qt picks up at runtime (WebP, AVIF, …) is automatically included.
src/app/MainWindow.cpp:116–120

QMessageBox Step 1

The simple way to show a user-visible error or confirmation. QMessageBox::warning, ::critical, ::information, ::question are static convenience calls. Use it whenever something goes wrong in a way the user should know about — not qDebug(), which only the developer sees.
src/app/MainWindow.cpp:125–128

7. Multimedia pipeline

QMediaPlayer — the playback engine Step 2

The high-level media-playback object in Qt Multimedia. You hand it a URL via setSource(), call play() / pause() / stop() / setPosition(), and it delegates to a platform backend (FFmpeg on your install) to decode audio and video. It exposes signals for playbackStateChanged, positionChanged, durationChanged, mediaStatusChanged, and errorOccurred. It does not render anything by itself — you give it a sink to send frames to.
src/media/VideoController.cpp:9–15

QVideoSink + QVideoFrame — the frame tap Step 2

QVideoSink is a frame consumer object. Attach it to a player with setVideoSink(sink) and decoded frames arrive as QVideoFrame objects via the videoFrameChanged signal — on the GUI thread. QVideoFrame holds the raw pixel data in whatever format the decoder produced (typically YUV from FFmpeg); frame.toImage() performs the colour conversion to QImage for display or inference. The alternative — QVideoWidget — renders directly to the screen but gives you no way to intercept frames, which would block Step 3 entirely.
src/media/VideoController.cpp:78–100

MediaStatus vs PlaybackState Step 2

Two different state machines on QMediaPlayer, easy to confuse:

  • PlaybackState: StoppedState / PlayingState / PausedState. What the user sees on the play/pause button.
  • MediaStatus: NoMedia → LoadingMedia → LoadedMedia → BufferingMedia → BufferedMedia → EndOfMedia, plus InvalidMedia on decode failure. The diagnostic state machine — this is what tells you why playback isn't progressing.

When something goes wrong, log mediaStatus transitions first; the PlaybackState will eventually catch up but tells you nothing about cause.
src/media/VideoController.cpp:120–147

8. UI patterns drawn from the codebase

Slider drag/update interlock Step 2

When the controller calls VideoControls::setPosition() 30×/second to advance the slider, that's fine — unless the user is mid-drag. Naïve code yanks the thumb out from under their finger. The fix is a small state machine: sliderPressed sets m_userIsDragging = true; sliderReleased clears it and emits a single seekRequested. While dragging, the controller's position updates are ignored. This is a generally applicable pattern any time external state and user input fight for the same widget.
src/ui/VideoControls.cpp:40–46,92–95

Controller as façade Step 2

VideoController hides QMediaPlayer entirely. Nothing outside VideoController.cpp includes <QMediaPlayer>. Two payoffs:

  • Encapsulation. Replacing Qt Multimedia with cv::VideoCapture or a streaming source is a single-file change.
  • Pipeline fork point. In Step 3, frameReady will fan out to both the on-screen views and an inference backend — doing that in the controller (one place) is cleaner than scattering it across MainWindow.

This is the controller from Model-View-Controller, but introduced only when a real engine exists to coordinate — not as a premature framework choice.

Widget emits intent, app dispatches Step 2

VideoControls doesn't own a QMediaPlayer; it emits playPauseClicked() / seekRequested(ms) and consumes setPosition(ms) / setPlaying(bool). MainWindow matches the two halves up. The widget could be driven by a unit test, an OpenCV-based controller, or a remote streaming pipeline without modification. General rule: UI widgets emit intent; application code dispatches it. This keeps GUI tests feasible and refactors local.

9. Deployment & runtime on Windows

Windows DLL search order Step 2

When the OS loads an executable, it resolves DLL references in roughly this order:

  1. The application directory.
  2. System32, SysWOW64.
  3. Directories listed in PATH.

So a Qt6Core.dll sitting next to your .exe always beats one on PATH. This matters when something has deployed Qt DLLs into your build/bin/ — you may be loading a different copy than you think.

Qt's plugin discovery (separate from the OS) Step 2

Qt's modules (Multimedia, image formats, platform integration, SQL drivers, etc.) are loaded at runtime from plugins/<category>/*.dll. Qt searches a list of paths returned by QCoreApplication::libraryPaths():

  1. The application directory + a plugins subfolder, if one exists.
  2. The path baked into Qt6Core.dll at the time Qt was built (usually the Qt install's plugins/ dir).
  3. Any directory pointed to by the QT_PLUGIN_PATH environment variable.

If a Qt6Core.dll from one Qt install ends up next to your .exe (typically copied there by a half-run of windeployqt), its baked-in path may not match where your plugins actually live, and things like QMediaPlayer silently become no-ops with Available backends QList(). Setting QT_PLUGIN_PATH in launch.json is the development fix; windeployqt doing a clean full deployment is the distribution fix.

windeployqt Step 2

Qt's bundled tool that walks an .exe, figures out which Qt DLLs and plugins it needs, and copies them next to the executable along with a generated qt.conf that fixes up the plugin search path. Run it once when you want a self-contained distribution; never run it half-way or you get the plugin discovery landmine.

C:\Qt\6.11.1\mingw_64\bin\windeployqt.exe `
    C:\Projects\InferenceVisualizer\build\bin\InferenceVisualizer.exe

The VS Code launch.json environment block Step 2

When you launch outside Qt Creator, four environment variables typically need to be set explicitly:

VariableWhy it's there
PATH Prepends Qt's bin/ and the MinGW runtime bin/ so the Windows loader finds Qt6Multimedia.dll, the FFmpeg DLLs, and libgcc_s_seh-1.dll. Without this: exit code 0xc0000135 (STATUS_DLL_NOT_FOUND).
QT_PLUGIN_PATH Points Qt at its plugins/ dir directly — bypasses any baked-in-path confusion.

10. Diagnostics & logging

Where qDebug() goes on Windows Step 2

On Windows, a Qt GUI app (linked with the WIN32 subsystem flag) detaches from the console. qDebug() output goes to OutputDebugString instead of stdout. VS Code's cppdbg debug console does not show OutputDebugString output — only Sysinternals' DbgView does. Qt Creator's "Application Output" pane captures it for you — so in Qt Creator it just works, anywhere else it appears to vanish.

qInstallMessageHandler — redirecting Qt logs Step 2

The robust workaround for the routing problem above: install a custom message handler that writes to a log file. The handler is called for every qDebug/qInfo/qWarning/qCritical/qFatal; we format, timestamp, and append. Truncating on each launch keeps the file scoped to one run.
src/main.cpp:24–65

QT_LOGGING_RULES Step 2

Qt's internal modules emit categorized debug output via qCDebug(...). Categories are off by default and turned on with the QT_LOGGING_RULES environment variable (e.g. qt.multimedia.*=true). Combined with the file message handler, this gives you a record of which plugin loaded, which codec was chosen, and why playback failed if it did.

11. Modern C++ patterns

#pragma once Step 1

Replaces traditional #ifndef/#define/#endif header guards. Supported by every modern compiler (GCC, Clang, MSVC), one line instead of three, no risk of macro-name collisions across files.

explicit on single-argument constructors Step 1

Prevents the compiler from using a constructor for an unintended implicit conversion. Without it, a function expecting ImageView would silently accept any QWidget* by wrapping it in a new ImageView. Always mark single-argument constructors explicit unless you want that conversion.
src/ui/ImageView.h:19 · src/app/MainWindow.h:13

override Step 1

Marks a function as intentionally overriding a virtual from a base class. If the base signature changes (e.g. Qt 7 renames or re-types resizeEvent), override turns a silent no-op into a compile error. Cheap insurance.
src/ui/ImageView.h:25

Forward declarations in headers Step 1

Headers like ImageView.h only need to know QLabel exists (it's a pointer member), not its full definition. A forward declaration class QLabel; avoids dragging the full <QLabel> header into every translation unit that includes ImageView.h. Faster builds and less coupling. Full includes go in the .cpp.
src/ui/ImageView.h:6–7 · src/app/MainWindow.h:5

Const-ref parameter passing for "big" types Step 1

setImage(const QImage& image) avoids copying the image into the function. In Qt's case QImage uses implicit sharing (copy-on-write), so even a by-value copy would be cheap until the image is modified — but const-ref expresses intent (we don't take ownership, we don't modify) and is the modern-C++ default for non-trivial types.
src/ui/ImageView.h:21

Raw pointers in Qt code Step 1

You'll see QLabel* m_label; rather than std::unique_ptr<QLabel>. This is correct in Qt: ownership is delegated to the parent-child tree (see parent-child ownership). For non-QObject types (e.g. an InferenceBackend we'll add in Step 3), we'll absolutely use std::unique_ptr. The two systems should not be mixed for the same object.

auto for local declarations Step 1

auto *fileMenu = menuBar()->addMenu(tr("&File")); — the type (QMenu*) is obvious from the right-hand side. auto shortens declarations and prevents accidental implicit conversions. Use it freely for locals; spell out types in interfaces (function parameters, return types).
src/app/MainWindow.cpp:60,62,66

Lambdas (captures, closures) Step 2

A lambda is a C++ closure — an anonymous function object that can capture local variables. In Qt code they're often the smallest path to a tiny slot:

connect(m_slider, &QSlider::sliderPressed, this,
        [this]() { m_userIsDragging = true; });

The capture [this] grabs the pointer so the body can touch members. Captures by reference ([&]) are risky in async contexts — if the referenced local goes out of scope before the lambda fires, you get a dangling reference. Capture by value ([=]) is safer when in doubt. See also Connecting to a lambda for the Qt-specific context-object requirement.

In-class member initialisers Step 2

quint64 m_frameCount{0}; and qint64 m_duration{0}; in the headers give a member a default value at the point of declaration. No need to repeat it in every constructor. The constructor's init list can still override per instance if needed. Modern C++11 feature, used everywhere now.
src/media/VideoController.h:52 · src/ui/VideoControls.h:32–34

Qt's fixed-width integer typedefs Step 2

qint64 and quint64 are Qt's portable signed/unsigned 64-bit integer types — identical to std::int64_t / std::uint64_t on every supported platform. QMediaPlayer's API uses qint64 for milliseconds, so we follow suit. Mixing int with qint64 is fine but generates implicit-conversion warnings under -Wconversion; sticking to the Qt type keeps the chain consistent.

12. Common pitfalls

Forgetting Q_OBJECT. Step 1 Without it, connect() compiles but does nothing — or you get undefined reference to vtable at link time. Any class with signals, slots, or properties needs it.
Using QPixmap off the GUI thread. Step 1 QPixmap is platform-tied to the display server. Loading or constructing one on a worker thread is an instant crash on Windows and undefined behavior elsewhere. Always do the QImage → QPixmap conversion on the GUI thread.
Rescaling an already-scaled pixmap. Step 1 Each scale-down loses information. If you scale on every resize starting from the previously-scaled pixmap, quality decays visibly. Always rescale from the original QImage (which is what ImageView::updateScaledPixmap() does).
Forgetting Qt::KeepAspectRatio. Step 1 The default is Qt::IgnoreAspectRatio, which stretches the image to fill the target. Easy mistake; obvious bug.
Double-parenting. Step 1 Passing a widget to a layout (layout->addWidget(child)) reparents it to the layout's owning widget. If you also passed a parent to its constructor, the new parent overrides — usually harmless, but worth knowing when debugging "why is this widget appearing nowhere?".
Mixing std::unique_ptr with Qt parent ownership. Step 1 If a QObject has a parent and sits inside a unique_ptr, both will try to delete it. Pick one ownership model per object.
Qt plugin not loaded — silent no-op. Step 2 When QMediaPlayer::play() does nothing and there's no error, the cause is almost always the multimedia plugin failing to load. Symptoms in the log: Available backends QList(), Failed to initialize QMediaPlayer "Not available". The fix on a dev box is QT_PLUGIN_PATH; on a deployed app, windeployqt.
qDebug() output invisible under VS Code. Step 2 Qt GUI apps on Windows route stdout to OutputDebugString, which cppdbg's console doesn't show. Always install a file-based message handler when you can't use Qt Creator — otherwise every diagnostic qDebug() you write vanishes into the void.
Mixing Qt installs by accident. Step 2 If something (Qt Creator's deploy step, a stray windeployqt run) copies Qt6Core.dll next to your .exe, Windows' DLL loader will pick that over anything on PATH because the application directory comes first in the search order. If the deployed copy is from a different Qt version than the rest of your environment, you get ABI-level confusion that's invisible until something fails strangely.
Slider fighting the user's finger. Step 2 Calling QSlider::setValue() from a position-update signal while the user is dragging makes the thumb jump. Always interlock with a "user is dragging" flag (pressed/released) and emit a single seek on release. See drag/update interlock.
Lambda connect() without a context object. Step 2 connect(sig, []() { /* uses captured this */ }); compiles and runs, but the connection lives forever — even after this is destroyed. Always pass this as the third argument so Qt automatically disconnects when the context object dies.
