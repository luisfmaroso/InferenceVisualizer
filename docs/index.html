1. Project overview

InferenceVisualizer is a desktop application for inspecting computer-vision inference results. Once complete it will load images and videos, run inference using YOLO, UNet, and arbitrary ONNX models, and display the original side-by-side with the processed output. The project doubles as a structured learning path through Qt Widgets, modern C++, and CMake on Windows — with the technical knowledge captured separately in the Qt & C++ concepts companion doc.

2. Current step Step 2 / 6

Step 2 adds video. The central widget is now a dual-pane QSplitter; the right pane mirrors the left until Step 3 routes it through inference. A VideoController hides QMediaPlayer behind a small façade (see controller as façade), a VideoControls widget gives play/pause + scrub, and the File menu gains Open Video…. Frames flow as QImage so later steps can hand them to an inference backend without changing the pipeline.

4. What was implemented

Step 1

  • A top-level QMainWindow with title, status bar, and a File menu containing Open Image… (Ctrl+O) and Exit (Ctrl+Q).
  • A reusable ImageView widget that displays a QImage scaled to fit while preserving aspect ratio.
  • Resize-safe rendering: the widget stores the original image and rescales from it on every resize, so quality never degrades from repeated scaling. (See rescale from the original.)
  • Robust file loading via QImageReader with EXIF orientation handling and per-file error reporting.
  • Two-tier CMake setup (root + src/) that scales as the project grows.
  • Warnings-as-feedback compile flags (-Wall -Wextra -Wpedantic on MinGW).

Step 2

  • The central widget is now a dual-pane QSplitter with two ImageViews (original and processed). The divider is draggable; panes can't collapse to zero. (See QSplitter.)
  • A VideoController wraps QMediaPlayer + QVideoSink behind a stable signal API. It emits frameReady(QImage) for every decoded frame, plus signals for state / position / duration / errors. (See QMediaPlayer, QVideoSink & QVideoFrame, signal forwarding.)
  • A VideoControls widget — play/pause button, position slider, time labels — that knows nothing about QMediaPlayer. It emits user-intent signals that MainWindow wires to the controller. (See widget emits intent.)
  • New menu entry Open Video… (Ctrl+Shift+O). Opening an image stops video playback; opening a video clears any displayed image.
  • Space-bar shortcut on the play/pause button. Slider has a drag/update interlock that prevents controller position updates from fighting the user's finger.
  • A file-based qInstallMessageHandler in main.cpp that mirrors all qDebug/qWarning/qCritical output to inference-visualizer.log next to the .exe — essential because Qt GUI apps on Windows route output through OutputDebugString, which VS Code's debug console doesn't show.
  • CMake now finds and links Qt6::Multimedia in addition to Qt6::Widgets.
  • A proper .gitignore finally added to keep build/ out of the repo.

5. Why it was implemented this way

5.1 Two-tier CMake

The root CMakeLists.txt answers "what is this project, and where is Qt?". The inner src/CMakeLists.txt answers "what files compile into the binary?". Keeping those two questions in separate files makes both easier to read and easier to grow. In Step 3, when an inference backend is added, only src/CMakeLists.txt changes — the root stays calm.

# CMakeLists.txt (root) — project metadata + Qt discovery only
cmake_minimum_required(VERSION 3.21)
project(InferenceVisualizer VERSION 0.1.0 LANGUAGES CXX)

set(CMAKE_CXX_STANDARD 17)
set(CMAKE_CXX_STANDARD_REQUIRED ON)
set(CMAKE_CXX_EXTENSIONS OFF)

find_package(Qt6 6.5 REQUIRED COMPONENTS Widgets Multimedia)
qt_standard_project_setup()
add_subdirectory(src)
# src/CMakeLists.txt — the actual executable target lives here
qt_add_executable(InferenceVisualizer
    WIN32
    main.cpp
)

target_sources(InferenceVisualizer PRIVATE
    app/MainWindow.h        app/MainWindow.cpp
    media/VideoController.h media/VideoController.cpp
    ui/ImageView.h          ui/ImageView.cpp
    ui/VideoControls.h      ui/VideoControls.cpp
)

target_link_libraries(InferenceVisualizer PRIVATE
    Qt6::Widgets
    Qt6::Multimedia
)

5.2 Hand-coded UI — no .ui Designer files

The original Qt Creator template included a mainwindow.ui XML file that uic compiles into a setupUi() call. That's fine for big static dialogs, but for a learning project it hides exactly the things we want to understand: every widget construction, every connect(), every parent assignment. Hand-coding the UI keeps everything visible and grep-able.

// src/app/MainWindow.cpp — the entire File menu, in plain C++
void MainWindow::buildMenus()
{
    auto *fileMenu = menuBar()->addMenu(tr("&File"));

    auto *openImageAction = fileMenu->addAction(tr("&Open Image..."));
    openImageAction->setShortcut(QKeySequence::Open);
    connect(openImageAction, &QAction::triggered, this, &MainWindow::openImage);

    auto *openVideoAction = fileMenu->addAction(tr("Open &Video..."));
    openVideoAction->setShortcut(QKeySequence(tr("Ctrl+Shift+O")));
    connect(openVideoAction, &QAction::triggered, this, &MainWindow::openVideo);

    fileMenu->addSeparator();

    auto *exitAction = fileMenu->addAction(tr("E&xit"));
    exitAction->setShortcut(QKeySequence::Quit);
    connect(exitAction, &QAction::triggered, qApp, &QApplication::quit);
}

Compare that with the equivalent .ui XML and a setupUi(this) call inside MainWindow::MainWindow — three lines of code, opaque to grep, generated by a tool you can't see. The code-first version is longer, but every action, shortcut, and connection is right there in front of you.

5.3 ImageView as its own widget, not a bare QLabel in MainWindow

It would have been one line to put a QLabel directly inside MainWindow. Instead, ImageView wraps the QLabel and owns the scaling logic. Why bother now? Because Step 2 feeds it video frames, Step 3 will feed it images with detection overlays, and Step 4 will feed it blended segmentation masks. All four use cases funnel through the same setImage(const QImage&) entry point. Centralizing the "how do I render a QImage in a Qt widget" question once, here, prevents the same scaling logic from being duplicated three times later.

// src/ui/ImageView.h — tiny stable API; all consumers go through setImage()
class ImageView : public QWidget
{
    Q_OBJECT
public:
    explicit ImageView(QWidget *parent = nullptr);

    void setImage(const QImage &image);   // the single entry point
    void clear();
    bool hasImage() const { return !m_original.isNull(); }

protected:
    void resizeEvent(QResizeEvent *event) override;   // resize-safe rescale

private:
    void updateScaledPixmap();
    QLabel *m_label;
    QImage  m_original;
};

5.4 Single pane in Step 1, splitter dual-pane in Step 2

The final UI is original-vs-processed side-by-side, but Step 1 had nothing to put in the right pane. Adding a placeholder then would have been misleading. In Step 2 the central widget becomes a QSplitter holding two ImageViews — a five-line refactor, not a rewrite, precisely because ImageView is already self-contained.

// src/app/MainWindow.cpp — the entire dual-pane refactor
void MainWindow::buildCentralWidget()
{
    auto *splitter = new QSplitter(Qt::Horizontal);
    splitter->addWidget(m_originalView);
    splitter->addWidget(m_processedView);
    splitter->setStretchFactor(0, 1);
    splitter->setStretchFactor(1, 1);
    splitter->setChildrenCollapsible(false);

    auto *container = new QWidget;
    auto *layout    = new QVBoxLayout(container);
    layout->setContentsMargins(0, 0, 0, 0);
    layout->addWidget(splitter, /*stretch=*/1);
    layout->addWidget(m_controls);

    setCentralWidget(container);
}

5.5 Why a VideoController object and not QMediaPlayer directly

MainWindow never sees a QMediaPlayer. It talks to VideoController, which exposes signals like frameReady(QImage), positionChanged(qint64), and slots like play(), pause(), seek(qint64). Two reasons:

  • Encapsulation. If Step 5 or a future plugin replaces Qt Multimedia with OpenCV's cv::VideoCapture or a streaming source, only VideoController changes — MainWindow compiles unchanged.
  • Pipeline fork point. In Step 3, VideoController::frameReady will fan out to both the on-screen views and an inference backend. Putting that fork inside the controller (one place) is cleaner than scattering it across MainWindow.

This is the controller as façade pattern, introduced only now that a real engine exists to coordinate — not as a premature framework choice.

// src/media/VideoController.h — the stable public face MainWindow sees
class VideoController : public QObject
{
    Q_OBJECT
public:
    bool openFile(const QString &path);

public slots:
    void play();
    void pause();
    void togglePlayPause();
    void stop();
    void seek(qint64 milliseconds);

signals:
    void frameReady(const QImage &image);
    void playbackStateChanged(QMediaPlayer::PlaybackState state);
    void positionChanged(qint64 milliseconds);
    void durationChanged(qint64 milliseconds);
    void errorOccurred(const QString &message);
    // QMediaPlayer is a private implementation detail, not on this API
};

5.6 Why VideoControls doesn't know about VideoController

The slider/button widget emits playPauseClicked, seekRequested(ms) and consumes setPosition(ms), setDuration(ms), setPlaying(bool). That's it. MainWindow connects the two halves. Why bother? Because this widget could be driven by a unit test, an OpenCV-based controller, or a remote streaming pipeline without modification. See widget emits intent, app dispatches for the general pattern.

// src/app/MainWindow.cpp — MainWindow is the only place that knows about both halves
void MainWindow::wireController()
{
    // Controller -> controls: keep slider/time label in sync
    connect(m_controller, &VideoController::durationChanged,
            m_controls,   &VideoControls::setDuration);
    connect(m_controller, &VideoController::positionChanged,
            m_controls,   &VideoControls::setPosition);

    // Controls -> controller: user intent
    connect(m_controls,   &VideoControls::playPauseClicked,
            m_controller, &VideoController::togglePlayPause);
    connect(m_controls,   &VideoControls::seekRequested,
            m_controller, &VideoController::seek);
}

5.7 Both panes show the same frame — for now

In Step 2 we connect VideoController::frameReady to both ImageViews. That's visually honest ("the dual pane works") without lying about inference being done. In Step 3 we replace one of those two connect() calls with a route through the inference backend — a one-line change.

// src/app/MainWindow.cpp — the two lines that Step 3 will partially rewire
connect(m_controller, &VideoController::frameReady,
        m_originalView,  &ImageView::setImage);

6. Build & run instructions

6.1 Path A — Qt Creator

  1. Open File → Open File or Project… and pick C:\Projects\InferenceVisualizer\CMakeLists.txt.
  2. Select the Desktop Qt 6.11.1 MinGW 64-bit kit, click Configure Project.
  3. Build with the hammer icon (or Ctrl+B), run with the green arrow (Ctrl+R).

6.2 Path B — VS Code (CMake Tools + C/C++ extensions)

The repo ships a .vscode/launch.json wired to the MinGW GDB at C:\Qt\Tools\mingw1310_64\bin\gdb.exe. Required extensions:

  • CMake Tools (ms-vscode.cmake-tools) — provides the ${command:cmake.launchTargetPath} used by launch.json.
  • C/C++ (ms-vscode.cpptools) — provides the cppdbg debugger type.

Flow:

  1. Open the project folder in VS Code.
  2. Pick the Qt 6.11.1 MinGW kit when CMake Tools prompts (or run CMake: Select a Kit).
  3. Press F5 — the preLaunchTask "CMake: build" runs first, then the debugger.

The populated environment block in launch.json (PATH, QT_PLUGIN_PATH, QT_MEDIA_BACKEND, QT_LOGGING_RULES) is essential when launching outside Qt Creator. See the env block explained for what each variable does and why each one is required.

6.3 Path C — command line

$env:PATH = "C:\Qt\Tools\mingw1310_64\bin;C:\Qt\Tools\Ninja;C:\Qt\Tools\CMake_64\bin;$env:PATH"

cmake -S C:\Projects\InferenceVisualizer `
      -B C:\Projects\InferenceVisualizer\build\cli `
      -G Ninja `
      -DCMAKE_BUILD_TYPE=Debug `
      -DCMAKE_PREFIX_PATH=C:\Qt\6.11.1\mingw_64

cmake --build C:\Projects\InferenceVisualizer\build\cli

C:\Projects\InferenceVisualizer\build\cli\bin\InferenceVisualizer.exe

The CLI build deliberately lives in build\cli\ so it doesn't fight with Qt Creator's build\Desktop_…_Debug\ directory.
