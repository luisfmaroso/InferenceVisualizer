1. Project overview

InferenceVisualizer is a desktop application for inspecting computer-vision inference results. Once complete it will load images and videos, run inference using YOLO, UNet, and arbitrary ONNX models, and display the original side-by-side with the processed output. The project doubles as a structured learning path through Qt Widgets, modern C++, and CMake on Windows — with the technical knowledge captured separately in the Qt & C++ concepts companion doc.

A new InferenceController in src/app/ orchestrates: receives QImage from VideoController, dispatches to the backend, emits a processed image (mask composited over the original with QPainter) for the right pane. New Inference menu adds Load Model, Run Inference toggle, and a Mask Opacity submenu.

4. What was implemented

Step 1

  • A top-level QMainWindow with title, status bar, and a File menu containing Open Image… (Ctrl+O) and Exit (Ctrl+Q).
  • A reusable ImageView widget that displays a QImage scaled to fit while preserving aspect ratio.
  • Resize-safe rendering: the widget stores the original image and rescales from it on every resize, so quality never degrades from repeated scaling. (See rescale from the original.)
  • Robust file loading via QImageReader with EXIF orientation handling and per-file error reporting.
  • Two-tier CMake setup (root + src/) that scales as the project grows.
  • Warnings-as-feedback compile flags (-Wall -Wextra -Wpedantic on MinGW).

Step 2

  • The central widget is now a dual-pane QSplitter with two ImageViews (original and processed). The divider is draggable; panes can't collapse to zero. (See QSplitter.)
  • A VideoController wraps QMediaPlayer + QVideoSink behind a stable signal API. It emits frameReady(QImage) for every decoded frame, plus signals for state / position / duration / errors. (See QMediaPlayer, QVideoSink & QVideoFrame, signal forwarding.)
  • A VideoControls widget — play/pause button, position slider, time labels — that knows nothing about QMediaPlayer. It emits user-intent signals that MainWindow wires to the controller. (See widget emits intent.)
  • New menu entry Open Video… (Ctrl+Shift+O). Opening an image stops video playback; opening a video clears any displayed image.
  • Space-bar shortcut on the play/pause button. Slider has a drag/update interlock that prevents controller position updates from fighting the user's finger.
  • A file-based qInstallMessageHandler in main.cpp that mirrors all qDebug/qWarning/qCritical output to inference-visualizer.log next to the .exe — essential because Qt GUI apps on Windows route output through OutputDebugString, which VS Code's debug console doesn't show.
  • CMake now finds and links Qt6::Multimedia in addition to Qt6::Widgets.
  • A proper .gitignore finally added to keep build/ out of the repo.

Step 3

  • New IInferenceBackend pure-virtual interface in src/inference/. Any backend (segmentation, detection, future model types) implements its four methods: loadModel, isReady, infer(QImage), setOverlayOpacity. (See IInferenceBackend.)
  • OnnxRunner — thin RAII wrapper around Ort::Env + Ort::Session. PIMPL'd so the ONNX Runtime C++ header only fans out to one .cpp. Loads an .onnx by path (UTF-8 → wchar_t on Windows), discovers input/output names from the graph, runs a single float tensor through. Shared by any future ONNX backend. (See OnnxRunner.)
  • OnnxSegmentationBackend implements IInferenceBackend for semantic-segmentation models. Resizes QImage to model input size, builds an NCHW float buffer with ImageNet normalization, runs through OnnxRunner, argmaxes the output over the channel axis, builds a colored class mask, composites it onto a copy of the original with QPainter. Per-class colors and visibility are configurable; defaults match a 2-class corrosion model (not-critical = dim yellow, critical = bold red). (See OnnxSegmentationBackend, QPainter overlays.)
  • InferenceController in src/app/: QObject orchestrator. Owns the backend via std::unique_ptr<IInferenceBackend>. Receives QImage frames, runs inference if enabled, emits processedFrameReady. Passthrough when disabled — keeps the dual-pane mirroring working without code branches in MainWindow. (See InferenceController.)
  • New Inference menu in MainWindow: Load Model… (Ctrl+M), Run Inference toggle (Ctrl+R, disabled until a model loads), Mask Opacity submenu (25 / 50 / 75% presets).
  • Right-pane wiring rewritten: instead of two direct connect(frameReady, ImageView::setImage) calls, the right pane now goes through InferenceController. Step 2's "both panes mirror" behavior is preserved by the controller emitting passthrough when inference is off.
  • CMake now finds and links the prebuilt ONNX Runtime (Microsoft's `onnxruntime-win-x64` zip; user installs to C:\Tools\onnxruntime). A post-build step copies onnxruntime.dll next to the executable so Windows finds it at launch.
  • .gitignore excludes models/ (trained .onnx files can be hundreds of MB).
  • New top-level SETUP_TOMORROW.md walks the user through ONNX Runtime download, Netron model inspection, and the one-off .pth → .onnx Python conversion.
  • Threading limitation documented: inference runs on the GUI thread. Images work instantly; video hitches per frame. Step 4 (formerly Step 6) targets a worker-thread inference setup.

5. Why it was implemented this way

5.1 Two-tier CMake

The root CMakeLists.txt answers "what is this project, and where is Qt?". The inner src/CMakeLists.txt answers "what files compile into the binary?". Keeping those two questions in separate files makes both easier to read and easier to grow. In Step 3, when an inference backend is added, only src/CMakeLists.txt changes — the root stays calm.

# CMakeLists.txt (root) — project metadata + Qt discovery only
cmake_minimum_required(VERSION 3.21)
project(InferenceVisualizer VERSION 0.1.0 LANGUAGES CXX)

set(CMAKE_CXX_STANDARD 17)
set(CMAKE_CXX_STANDARD_REQUIRED ON)
set(CMAKE_CXX_EXTENSIONS OFF)

find_package(Qt6 6.5 REQUIRED COMPONENTS Widgets Multimedia)
qt_standard_project_setup()
add_subdirectory(src)
# src/CMakeLists.txt — the actual executable target lives here
qt_add_executable(InferenceVisualizer
    WIN32
    main.cpp
)

target_sources(InferenceVisualizer PRIVATE
    app/MainWindow.h        app/MainWindow.cpp
    media/VideoController.h media/VideoController.cpp
    ui/ImageView.h          ui/ImageView.cpp
    ui/VideoControls.h      ui/VideoControls.cpp
)

target_link_libraries(InferenceVisualizer PRIVATE
    Qt6::Widgets
    Qt6::Multimedia
)

5.2 Hand-coded UI — no .ui Designer files

The original Qt Creator template included a mainwindow.ui XML file that uic compiles into a setupUi() call. That's fine for big static dialogs, but for a learning project it hides exactly the things we want to understand: every widget construction, every connect(), every parent assignment. Hand-coding the UI keeps everything visible and grep-able.

// src/app/MainWindow.cpp — the entire File menu, in plain C++
void MainWindow::buildMenus()
{
    auto *fileMenu = menuBar()->addMenu(tr("&File"));

    auto *openImageAction = fileMenu->addAction(tr("&Open Image..."));
    openImageAction->setShortcut(QKeySequence::Open);
    connect(openImageAction, &QAction::triggered, this, &MainWindow::openImage);

    auto *openVideoAction = fileMenu->addAction(tr("Open &Video..."));
    openVideoAction->setShortcut(QKeySequence(tr("Ctrl+Shift+O")));
    connect(openVideoAction, &QAction::triggered, this, &MainWindow::openVideo);

    fileMenu->addSeparator();

    auto *exitAction = fileMenu->addAction(tr("E&xit"));
    exitAction->setShortcut(QKeySequence::Quit);
    connect(exitAction, &QAction::triggered, qApp, &QApplication::quit);
}

Compare that with the equivalent .ui XML and a setupUi(this) call inside MainWindow::MainWindow — three lines of code, opaque to grep, generated by a tool you can't see. The code-first version is longer, but every action, shortcut, and connection is right there in front of you.

5.3 ImageView as its own widget, not a bare QLabel in MainWindow

It would have been one line to put a QLabel directly inside MainWindow. Instead, ImageView wraps the QLabel and owns the scaling logic. Why bother now? Because Step 2 feeds it video frames, Step 3 will feed it images with detection overlays, and Step 4 will feed it blended segmentation masks. All four use cases funnel through the same setImage(const QImage&) entry point. Centralizing the "how do I render a QImage in a Qt widget" question once, here, prevents the same scaling logic from being duplicated three times later.

// src/ui/ImageView.h — tiny stable API; all consumers go through setImage()
class ImageView : public QWidget
{
    Q_OBJECT
public:
    explicit ImageView(QWidget *parent = nullptr);

    void setImage(const QImage &image);   // the single entry point
    void clear();
    bool hasImage() const { return !m_original.isNull(); }

protected:
    void resizeEvent(QResizeEvent *event) override;   // resize-safe rescale

private:
    void updateScaledPixmap();
    QLabel *m_label;
    QImage  m_original;
};

5.4 Single pane in Step 1, splitter dual-pane in Step 2

The final UI is original-vs-processed side-by-side, but Step 1 had nothing to put in the right pane. Adding a placeholder then would have been misleading. In Step 2 the central widget becomes a QSplitter holding two ImageViews — a five-line refactor, not a rewrite, precisely because ImageView is already self-contained.

// src/app/MainWindow.cpp — the entire dual-pane refactor
void MainWindow::buildCentralWidget()
{
    auto *splitter = new QSplitter(Qt::Horizontal);
    splitter->addWidget(m_originalView);
    splitter->addWidget(m_processedView);
    splitter->setStretchFactor(0, 1);
    splitter->setStretchFactor(1, 1);
    splitter->setChildrenCollapsible(false);

    auto *container = new QWidget;
    auto *layout    = new QVBoxLayout(container);
    layout->setContentsMargins(0, 0, 0, 0);
    layout->addWidget(splitter, /*stretch=*/1);
    layout->addWidget(m_controls);

    setCentralWidget(container);
}

5.5 Why a VideoController object and not QMediaPlayer directly

MainWindow never sees a QMediaPlayer. It talks to VideoController, which exposes signals like frameReady(QImage), positionChanged(qint64), and slots like play(), pause(), seek(qint64). Two reasons:

  • Encapsulation. If Step 5 or a future plugin replaces Qt Multimedia with OpenCV's cv::VideoCapture or a streaming source, only VideoController changes — MainWindow compiles unchanged.
  • Pipeline fork point. In Step 3, VideoController::frameReady will fan out to both the on-screen views and an inference backend. Putting that fork inside the controller (one place) is cleaner than scattering it across MainWindow.

This is the controller as façade pattern, introduced only now that a real engine exists to coordinate — not as a premature framework choice.

// src/media/VideoController.h — the stable public face MainWindow sees
class VideoController : public QObject
{
    Q_OBJECT
public:
    bool openFile(const QString &path);

public slots:
    void play();
    void pause();
    void togglePlayPause();
    void stop();
    void seek(qint64 milliseconds);

signals:
    void frameReady(const QImage &image);
    void playbackStateChanged(QMediaPlayer::PlaybackState state);
    void positionChanged(qint64 milliseconds);
    void durationChanged(qint64 milliseconds);
    void errorOccurred(const QString &message);
    // QMediaPlayer is a private implementation detail, not on this API
};

5.6 Why VideoControls doesn't know about VideoController

The slider/button widget emits playPauseClicked, seekRequested(ms) and consumes setPosition(ms), setDuration(ms), setPlaying(bool). That's it. MainWindow connects the two halves. Why bother? Because this widget could be driven by a unit test, an OpenCV-based controller, or a remote streaming pipeline without modification. See widget emits intent, app dispatches for the general pattern.

// src/app/MainWindow.cpp — MainWindow is the only place that knows about both halves
void MainWindow::wireController()
{
    // Controller -> controls: keep slider/time label in sync
    connect(m_controller, &VideoController::durationChanged,
            m_controls,   &VideoControls::setDuration);
    connect(m_controller, &VideoController::positionChanged,
            m_controls,   &VideoControls::setPosition);

    // Controls -> controller: user intent
    connect(m_controls,   &VideoControls::playPauseClicked,
            m_controller, &VideoController::togglePlayPause);
    connect(m_controls,   &VideoControls::seekRequested,
            m_controller, &VideoController::seek);
}

5.10 Why IInferenceBackend as an interface with one implementation

Step 3 ships a single backend (segmentation). Why an interface at all?

  • The right place for backend-specific logic. Mask compositing is segmentation-specific — box drawing would be detection-specific. Both should live in the backend that knows what its output means. InferenceController stays generic; it doesn't grow a giant if/else when a second backend lands.
  • Cheap to add now, expensive later. Once MainWindow grows to call backend->runSegmentation() directly, retrofitting the interface means touching every call site. One file of overhead today vs. a refactor across three files tomorrow.
// src/inference/IInferenceBackend.h — the contract every backend satisfies
class IInferenceBackend
{
public:
    virtual ~IInferenceBackend() = default;

    virtual bool    loadModel(const QString &path) = 0;
    virtual bool    isReady() const = 0;
    virtual QString errorString() const = 0;
    virtual QImage  infer(const QImage &input) = 0;
    virtual void    setOverlayOpacity(double opacity) = 0;
};

5.11 Why mask compositing lives in the backend, not the controller

One way to design this would be: backend returns a class-id mask, controller paints colors. We don't do that. The backend returns a fully-composited QImage ready to display. Reason: different backends produce different overlay shapes — segmentation paints masks, detection draws boxes, classification draws a label corner. If the controller knew how to render any of them, it would need a discriminated union of result types and a switch over kinds. By making "render to a QImage" part of the backend's contract, the controller stays one signal in, one signal out, regardless of which model is loaded.

// src/inference/OnnxSegmentationBackend.cpp — backend does the QPainter composite itself
QImage OnnxSegmentationBackend::compositeOverlay(
    const QImage &original,
    const QImage &mask) const
{
    QImage result = original.convertToFormat(QImage::Format_ARGB32);

    QPainter painter(&result);
    painter.setRenderHint(QPainter::SmoothPixmapTransform, false);
    painter.setOpacity(m_opacity);
    painter.drawImage(0, 0, mask);
    painter.end();

    return result;
}

5.12 Why OnnxRunner is a separate helper class

Loading a .onnx, managing the Ort::Env + Ort::Session lifetime, the Windows-specific wchar_t path conversion, the input/output name discovery, the float-tensor packing for Ort::Value — all of that is identical for every ONNX-based backend. Putting it inside OnnxSegmentationBackend would be fine today; tomorrow, when an OnnxDetectionBackend lands, we'd either duplicate the code or extract it then. Doing the extraction now means the second backend only writes its own pre/post-processing, not 60 lines of ORT plumbing again.

// src/inference/OnnxSegmentationBackend.h — backend owns a runner, isn't one
class OnnxSegmentationBackend : public IInferenceBackend
{
    // ...
private:
    Config                       m_cfg;
    std::unique_ptr<OnnxRunner>  m_runner;       // future detection backend reuses the same class
    std::vector<float>           m_inputBuffer;  // reused across frames to avoid alloc churn
    QString                      m_lastError;
    double                       m_opacity = 0.5;
};

5.13 Why InferenceController passes through when disabled

The simpler-sounding design is: MainWindow connects frameReady to the right pane or to the inference pipeline, depending on the toggle, and reconnects on every flip. That means signal connections change at runtime, which is ugly and bug-prone.

The actual design is: InferenceController always receives every frame and always emits a processed frame — but when disabled, the emitted frame is the input unchanged. MainWindow wires once; the toggle just flips a boolean inside the controller. As a bonus, the right pane keeps mirroring the left exactly the way Step 2 set it up.

5.14 FIFO + backpressure for video (process every frame)

Inference at 100–3000 ms per frame on the GUI thread is much slower than 33 ms (30 FPS). Two ways to bound the resulting backlog:

  • Drop intermediate frames — one-slot buffer, each new frame replaces the old. Right when you only care about "the most recent" (real-time monitoring).
  • FIFO + backpressure to the source — queue every frame in order, pause the producer when the queue grows past a high watermark, resume when it drains. Right when you can't afford to lose any frame (batch/offline inference, what the user actually wants).

We picked option two. InferenceController appends each frame to a FIFO, signals wantsSourcePaused(true) when the queue passes a high watermark, processes frames one at a time via Qt::QueuedConnection self-reinvocation (so paint events for the original pane can fire between inferences), and signals wantsSourcePaused(false) when the queue drains.

// src/app/InferenceController.cpp — FIFO + backpressure
void InferenceController::processFrame(const QImage &input)
{
    if (!m_enabled || !isReady() || input.isNull()) {
        emit processedFrameReady(input);
        return;
    }
    m_frameQueue.enqueue(input);            // every frame preserved
    if (!m_backpressured && m_frameQueue.size() >= m_highWatermark) {
        m_backpressured = true;
        emit wantsSourcePaused(true);       // MainWindow pauses the video
    }
    if (!m_busy) {
        m_busy = true;
        QMetaObject::invokeMethod(this,
            &InferenceController::runNextQueuedFrame,
            Qt::QueuedConnection);
    }
}

void InferenceController::runNextQueuedFrame()
{
    if (m_frameQueue.isEmpty() || !isReady() || !m_enabled) {
        m_busy = false;
        if (m_backpressured) {
            m_backpressured = false;
            emit wantsSourcePaused(false);
        }
        return;
    }
    QImage frame = m_frameQueue.dequeue();
    QImage result = m_backend->infer(frame);
    emit processedFrameReady(result.isNull() ? frame : result);

    if (m_backpressured && m_frameQueue.size() <= m_lowWatermark) {
        m_backpressured = false;
        emit wantsSourcePaused(false);
    }

    if (!m_frameQueue.isEmpty()) {
        QMetaObject::invokeMethod(this,
            &InferenceController::runNextQueuedFrame,
            Qt::QueuedConnection);          // re-queue, NOT tight-loop
    } else {
        m_busy = false;
    }
}
// src/app/MainWindow.cpp — forward backpressure to the video player
void MainWindow::onInferenceWantsSourcePaused(bool paused)
{
    if (paused) {
        if (m_controller->playbackState() == QMediaPlayer::PlayingState) {
            m_controller->pause();
            m_pausedByBackpressure = true;
        }
    } else {
        if (m_pausedByBackpressure) {       // only resume what WE paused
            m_pausedByBackpressure = false;
            m_controller->play();
        }
    }
}

User experience with slow CPU inference: the video plays in bursts — decode a couple frames, queue fills, pause, inference grinds, resume. Every frame in the source video appears on the processed pane in native order. Memory stays bounded at the high watermark. The m_pausedByBackpressure flag distinguishes "we paused" from "user paused" so user pauses are never auto-resumed.

The real fix for slow video is Step 4 worker-thread inference; the FIFO + backpressure shape is still correct for that, with the inference happening off-thread.

5.15 Why ORT initialization is constructor-time, not per-frame

Ort::Env creation is heavy (several ms), and the session itself loads model weights into memory once and reuses them. We construct both once when InferenceController is built and keep them alive until the controller dies. Per-frame work is just Session::Run with a fresh tensor view. Putting any of this in the per-frame path would multiply latency by 10×.

// src/inference/OnnxRunner.cpp — Env + SessionOptions live for the runner's lifetime
struct OnnxRunner::Impl {
    Ort::Env                          env{ORT_LOGGING_LEVEL_WARNING,
                                          "InferenceVisualizer"};
    Ort::SessionOptions               options;
    std::unique_ptr<Ort::Session>     session;    // created once, in loadModel()
    Ort::AllocatorWithDefaultOptions  allocator;
    std::vector<Ort::Value>           lastOutputs;
};

6. Build & run instructions

6.1 Path A — Qt Creator

  1. Open File → Open File or Project… and pick C:\Projects\InferenceVisualizer\CMakeLists.txt.
  2. Select the Desktop Qt 6.11.1 MinGW 64-bit kit, click Configure Project.
  3. Build with the hammer icon (or Ctrl+B), run with the green arrow (Ctrl+R).

6.2 Path B — VS Code (CMake Tools + C/C++ extensions)

The repo ships a .vscode/launch.json wired to the MinGW GDB at C:\Qt\Tools\mingw1310_64\bin\gdb.exe. Required extensions:

  • CMake Tools (ms-vscode.cmake-tools) — provides the ${command:cmake.launchTargetPath} used by launch.json.
  • C/C++ (ms-vscode.cpptools) — provides the cppdbg debugger type.

Flow:

  1. Open the project folder in VS Code.
  2. Pick the Qt 6.11.1 MinGW kit when CMake Tools prompts (or run CMake: Select a Kit).
  3. Press F5 — the preLaunchTask "CMake: build" runs first, then the debugger.

The populated environment block in launch.json (PATH, QT_PLUGIN_PATH, QT_MEDIA_BACKEND, QT_LOGGING_RULES) is essential when launching outside Qt Creator. See the env block explained for what each variable does and why each one is required.

If you put it somewhere else, override at configure time: cmake -DONNXRUNTIME_DIR=/opt/onnxruntime ...

Drop your model

# MainWindow auto-loads model_tcc.onnx from the same dir as the .exe.
cp /path/to/your/model_tcc.onnx ~/InferenceVisualizer/build/bin/

Build & run from VS Code

  1. Open the project folder in VS Code.
  2. Install CMake Tools and C/C++ extensions if not already.
  3. Pick the GCC kit when CMake Tools prompts.
  4. In the Run & Debug panel, pick "Debug Qt Application (GDB, Linux)" from the dropdown.
  5. Press F5. The preLaunchTask builds first, then GDB launches the binary.

Build & run from the terminal

cmake -S ~/InferenceVisualizer -B ~/InferenceVisualizer/build -G Ninja \
      -DCMAKE_BUILD_TYPE=Debug

cmake --build ~/InferenceVisualizer/build

LD_LIBRARY_PATH=~/onnxruntime/lib:$LD_LIBRARY_PATH \
    ~/InferenceVisualizer/build/bin/InferenceVisualizer

The LD_LIBRARY_PATH prefix is required because Linux's loader doesn't search the application directory by default (unlike Windows). The .vscode/launch.json Linux configuration sets this automatically for debug runs.
