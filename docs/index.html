1. Project overview

InferenceVisualizer is a desktop application for inspecting computer-vision inference results. Once complete it will load images and videos, run inference using YOLO, UNet, and arbitrary ONNX models, and display the original side-by-side with the processed output. The project doubles as a structured learning path through Qt Widgets, modern C++, and CMake on Windows.

2. Current step Step 1 / 6

Step 1 delivers the foundation: a main window with a menu bar, a working Open Image action, and a reusable widget that displays images scaled to fit. No inference, no video — but the seams that later steps will plug into are in place.

4. What was implemented

  • A top-level QMainWindow with title, status bar, and a File menu containing Open Image… (Ctrl+O) and Exit (Ctrl+Q).
  • A reusable ImageView widget that displays a QImage scaled to fit while preserving aspect ratio.
  • Resize-safe rendering: the widget stores the original image and rescales from it on every resize, so quality never degrades from repeated scaling.
  • Robust file loading via QImageReader: respects EXIF orientation, automatically pulls in all formats Qt's image plugins support (PNG, JPEG, BMP, TIFF, WebP, …), and reports the actual failure reason via QMessageBox on bad input.
  • Two-tier CMake setup (root + src/) that scales as the project grows.
  • Warnings-as-feedback compile flags (-Wall -Wextra -Wpedantic on MinGW).

5. Why it was implemented this way

5.1 Two-tier CMake

The root CMakeLists.txt answers "what is this project, and where is Qt?". The inner src/CMakeLists.txt answers "what files compile into the binary?". Keeping those two questions in separate files makes both easier to read and easier to grow. In Step 3, when an inference backend is added, only src/CMakeLists.txt changes — the root stays calm.

5.2 Hand-coded UI — no .ui Designer files

The original Qt Creator template included a mainwindow.ui XML file that uic compiles into a setupUi() call. That's fine for big static dialogs, but for a learning project it hides exactly the things we want to understand: every widget construction, every connect(), every parent assignment. Hand-coding the UI keeps everything visible and grep-able.

5.3 ImageView as its own widget, not a bare QLabel in MainWindow

It would have been one line to put a QLabel directly inside MainWindow. Instead, ImageView wraps the QLabel and owns the scaling logic. Why bother now? Because Step 2 will feed it video frames, Step 3 will feed it images with detection overlays, and Step 4 will feed it blended segmentation masks. All four use cases funnel through the same setImage(const QImage&) entry point. Centralizing the "how do I render a QImage in a Qt widget" question once, here, prevents the same scaling logic from being duplicated three times later.

5.4 Single pane in Step 1, splitter dual-pane in Step 2

The final UI is original-vs-processed side-by-side, but Step 1 has nothing to put in the right pane. Adding a placeholder now would be misleading. In Step 2 the central widget becomes a QSplitter holding two ImageViews — a five-line refactor, not a rewrite, precisely because ImageView is already self-contained.

6. Qt concepts learned

6.1 QApplication and the event loop

Every Qt GUI begins with a QApplication. It initializes the GUI subsystem, parses Qt-specific command-line flags (-style, -platform, …), and — crucially — runs the event loop when you call exec(). The event loop is the heartbeat of any Qt GUI: it pulls events (mouse, keyboard, paint, timer) from the OS and dispatches them to widgets. Without it, your window appears and instantly closes.
src/main.cpp:7–13

6.2 QMainWindow vs plain QWidget

QMainWindow is a specialized window that provides slots for a menu bar, status bar, toolbars, dock widgets, and a single central widget. Use it for the top-level window. Use plain QWidget (or a subclass) for custom widgets that live inside other widgets — like our ImageView.
src/app/MainWindow.h:8 · src/ui/ImageView.h:8

6.3 The Q_OBJECT macro and the MOC

Any class that uses signals, slots, properties, or runtime type info needs Q_OBJECT in its declaration. The macro declares hidden meta-object members; the Meta-Object Compiler (MOC) reads your header at build time and generates a moc_*.cpp file with their implementations. Without Q_OBJECT, connect() calls compile but silently fail to fire — or you get "undefined reference to vtable" link errors. CMake's AUTOMOC (enabled by qt_standard_project_setup()) runs MOC for you on any header containing the macro.
src/app/MainWindow.h:10 · src/ui/ImageView.h:16

6.4 Parent–child ownership

When you pass a parent pointer to a QObject constructor — new QLabel(this) — the child is added to the parent's child list. When the parent is destroyed, Qt walks that list and deletes every child. This is why raw new/delete in Qt code isn't a leak: the lifetime is encoded in the parent tree, not in std::unique_ptr. Don't mix the two for the same object.
src/ui/ImageView.cpp:12 · src/app/MainWindow.cpp:18

6.5 Signals & slots (modern syntax)

A signal is emitted when something happens (QAction::triggered fires when the user clicks the menu entry). A slot is a function that runs in response. connect() wires them together. We use the function-pointer form:

connect(openAction, &QAction::triggered, this, &MainWindow::openImage);

This is checked at compile time — if the signal doesn't exist or the slot signature doesn't match, you get an error. The old string-based form SIGNAL(triggered())/SLOT(openImage()) is checked at runtime and fails silently on typos. Always prefer the function-pointer form.
src/app/MainWindow.cpp:33,40

6.6 QAction, QMenu, QMenuBar

An action represents something the user can do, decoupled from where it appears. The same QAction can live in a menu, a toolbar, and a context menu simultaneously, with one shortcut and one icon. We don't exploit this in Step 1, but it's the reason Qt models commands this way.
src/app/MainWindow.cpp:26–42

6.7 QFileDialog::getOpenFileName

A static convenience function that pops up the OS file picker and blocks until the user chooses a file or cancels. Returns an empty QString on cancel — not an error, just nothing to do.
src/app/MainWindow.cpp:54–58

6.8 QImage vs QPixmap

Two pixel containers, used at different stages of the pipeline:

QImageQPixmap
Lives onCPU memoryDisplay server / GPU (platform-dependent)
Thread-safe?Yes — safe to create/use on any threadNo — GUI thread only
Best forLoading, processing, inference, storageDrawing to a widget

Rule of thumb: store QImage, convert to QPixmap at the last moment when assigning to a QLabel. This rule will matter a great deal in Step 3, when inference runs on a worker thread — the result must come back as a QImage.
src/ui/ImageView.cpp:55–65

6.9 QImageReader over QImage(path)

Both can load images, but QImageReader exposes errorString(), lets you query the file's format without loading it, and provides setAutoTransform(true) to honour EXIF orientation (so phone photos don't appear sideways). The constructor form gives you a generic null image on failure with no clue why.
src/app/MainWindow.cpp:60–72

6.10 resizeEvent

Qt delivers events to widgets through virtual methods on QWidget: paintEvent, mousePressEvent, resizeEvent, … Override the one you care about. Always call the base-class implementation (QWidget::resizeEvent(event)) unless you specifically intend to suppress the default behaviour.
src/ui/ImageView.cpp:39–45

6.11 Layouts

QVBoxLayout, QHBoxLayout, and friends handle widget positioning and resize propagation automatically. We use a zero-margin QVBoxLayout in ImageView to make the internal QLabel fill the widget. Hand-rolling setGeometry() works but is fragile — always reach for a layout first.
src/ui/ImageView.cpp:19–22

6.12 tr() for translatable strings

Every user-visible string is wrapped in tr("…"). Even with no translation files today, the habit costs nothing and means localizing later is a tooling problem instead of a refactor.

7. C++ concepts learned

7.1 #pragma once

Replaces traditional #ifndef/#define/#endif header guards. Supported by every modern compiler (GCC, Clang, MSVC), one line instead of three, no risk of macro-name collisions across files.

7.2 explicit on single-argument constructors

Prevents the compiler from using a constructor for an unintended implicit conversion. Without it, a function expecting ImageView would silently accept any QWidget* by wrapping it in a new ImageView. Always mark single-argument constructors explicit unless you want that conversion.
src/ui/ImageView.h:19 · src/app/MainWindow.h:13

7.3 override

Marks a function as intentionally overriding a virtual from a base class. If the base signature changes (e.g. Qt 7 renames or re-types resizeEvent), override turns a silent no-op into a compile error. Cheap insurance.
src/ui/ImageView.h:25

7.4 Forward declarations in headers

Headers like ImageView.h only need to know QLabel exists (it's a pointer member), not its full definition. A forward declaration class QLabel; avoids dragging the full <QLabel> header into every translation unit that includes ImageView.h. Faster builds and less coupling. Full includes go in the .cpp.
src/ui/ImageView.h:6–7 · src/app/MainWindow.h:5

7.5 Const-ref parameter passing for "big" types

setImage(const QImage& image) avoids copying the image into the function. In Qt's case QImage uses implicit sharing (copy-on-write), so even a by-value copy would be cheap until the image is modified — but const-ref expresses intent (we don't take ownership, we don't modify) and is the modern-C++ default for non-trivial types.
src/ui/ImageView.h:21

7.6 Raw pointers in Qt code

You'll see QLabel* m_label; rather than std::unique_ptr<QLabel>. This is correct in Qt: ownership is delegated to the parent — child tree (see §6.4). For non-QObject types (e.g. an InferenceBackend we'll add in Step 3), we'll absolutely use std::unique_ptr. The two systems should not be mixed for the same object.

7.7 auto for local declarations

auto *fileMenu = menuBar()->addMenu(tr("&File")); — the type (QMenu*) is obvious from the right-hand side. auto shortens declarations and prevents accidental implicit conversions. Use it freely for locals; spell out types in interfaces (function parameters, return types).
src/app/MainWindow.cpp:28,32,39

8. Build & run instructions

  1. Open File → Open File or Project… and pick C:\Projects\InferenceVisualizer\CMakeLists.txt.
  2. Select the Desktop Qt 6.11.1 MinGW 64-bit kit, click Configure Project.

The repo ships a .vscode/launch.json wired to the MinGW GDB at C:\Qt\Tools\mingw1310_64\bin\gdb.exe. Required extensions:

  • CMake Tools (ms-vscode.cmake-tools) — provides the ${command:cmake.launchTargetPath} used by launch.json.
  • C/C++ (ms-vscode.cpptools) — provides the cppdbg debugger type.

Flow:

  1. Open the project folder in VS Code.
  2. Pick the Qt 6.11.1 MinGW kit when CMake Tools prompts (or run CMake: Select a Kit).
  3. Press F7 to build, then F5 to launch with the debugger.

9. Common pitfalls

Forgetting Q_OBJECT. Without it, connect() compiles but does nothing — or you get undefined reference to vtable at link time. Any class with signals, slots, or properties needs it.
Using QPixmap off the GUI thread. QPixmap is platform-tied to the display server. Loading or constructing one on a worker thread is an instant crash on Windows and undefined behavior elsewhere. Always do the QImage → QPixmap conversion on the GUI thread.
Rescaling an already-scaled pixmap. Each scale-down loses information. If you scale on every resize starting from the previously-scaled pixmap, quality decays visibly. Always rescale from the original QImage (which is what ImageView::updateScaledPixmap() does).
Forgetting Qt::KeepAspectRatio. The default is Qt::IgnoreAspectRatio, which stretches the image to fill the target. Easy mistake; obvious bug.
Double-parenting. Passing a widget to a layout (layout->addWidget(child)) reparents it to the layout's owning widget. If you also passed a parent to its constructor, the new parent overrides — usually harmless, but worth knowing when debugging "why is this widget appearing nowhere?".
Mixing std::unique_ptr with Qt parent ownership. If a QObject has a parent and sits inside a unique_ptr, both will try to delete it. Pick one ownership model per object.
